模型返回了工具名称和参数，业务任务就完成了吗？本文讨论应用自行提供的工具：模型提出请求，程序执行、核对结果，再将状态交回。以下退款查询是结合 LangChain 英文官方文档整理的设计推演，不是个人项目的已实现功能或生产事故复盘。

## 目录

## 场景：一次退款汇总请求

假设运营提问：“查询上月成功退款金额，按渠道汇总。”应用向模型提供一个只读汇总工具，参数包含日期范围和渠道。模型可能请求错误日期、遗漏统计条件，或继续提出并未开放的退款操作。

工具契约需要说明用途、输入与返回结构；参数可解析只是开始。LangChain 的工具说明介绍了输入 schema 和运行时上下文，而模型文档展示了工具请求、执行和结果回传的过程。[工具说明](https://docs.langchain.com/oss/python/langchain/tools)、[模型与工具调用](https://docs.langchain.com/oss/python/langchain/models)

## 请求先经过应用检查

在这个方案里，执行器首先确认工具在允许列表中，再检查日期顺序、最大跨度、渠道枚举和结果规模。缺少条件时要求补充，错误参数返回可修正信息，不默默替换成一段可能改变业务含义的查询。

身份和数据范围由已认证的应用上下文决定。即使模型传入另一个用户或商户标识，执行器也不能据此扩大查询范围。对模型隐藏某个工具有助于减少误选，真正的权限限制仍需落在执行路径和数据访问层。

只读汇总与退款写操作分开设计。当前案例只开放查询；若以后增加写工具，应另外定义授权、确认、幂等和审计要求，不能因为模型说“用户已同意”就直接执行。

## 返回状态也属于工具契约

一次调用至少要能区分成功、有权限但无数据、参数错误、权限拒绝和服务失败。成功结果包含统计口径与数据来源；失败结果说明可以修正还是应该停止。模型不能把“查询失败”改写成“退款金额为零”。

请求标识、工具调用标识和尝试次数用于关联记录，日期与统计状态等关键参数保留在轨迹中。结果过长时，返回摘要与可回查产物；不让大段无关输出耗尽下一轮上下文，也不把凭证或内部错误堆栈交给模型。

## 什么时候重试，什么时候停止

模型重复提出同一调用，不代表值得再次执行。可以用工具名和规范化参数识别重复请求，并检查上一次结果是否仍有效。对暂时性服务错误采用有限重试；参数不合法则等待修正，权限拒绝不靠重复请求绕过。

设计还需要最大调用次数与总耗时预算。演示可以先设最多三轮工具调用，到达边界就返回已获得的结果和未完成原因；具体阈值需用任务记录调整。预算在程序执行层检查，不能只在 Prompt 里要求模型“适可而止”。

超时也不等于底层任务一定没有执行。只读查询可以在确认边界后重试；涉及写入时，应先确认状态或利用幂等机制，避免盲目重复。前端停止展示后，仍要记录后端是否取消成功，不能把界面关闭视为执行终止。

## 用哪些检查项验收

| 检查输入或现象 | 预期核查点 |
| --- | --- |
| 日期反转、跨度过大 | 执行前拒绝或要求修正，数据库未接受无效请求 |
| 请求未开放的写工具 | 应用拒绝，不能变成隐含的退款操作 |
| 参数携带其他用户标识 | 不扩大已认证用户的数据范围 |
| 查询成功但没有记录 | 明确“无数据”，与服务异常分别呈现 |
| 相同失败调用反复出现 | 触发次数或耗时限制，保留停止原因 |

验证时保存请求参数、校验结果、实际调用、返回状态与后续回答，检查每一步是否真的发生。这样的记录才能支持“执行受到控制”的判断；仅有一段流畅的最终回答，不能证明工具正确执行。
