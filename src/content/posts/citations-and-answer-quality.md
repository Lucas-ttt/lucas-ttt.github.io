给版本检索工具补引用时，我先做了一个很小的实验：工具返回 `csv-v2`，展示的建议却写成“添加 user_id”，旁边仍然挂着合法的 `csv-v2`。检查引用 ID 的程序没有报错，但 v2 文档要求的实际字段是 `customer_id`。这个反例让我把引用校验从一个笼统的开关，拆成了来源关联、适用条件和结论支持三个层次。

这次我先实现前两层，使用三份自编排障资料和一个只读检索函数，不请求模型。这样可以直接观察检查器接收了什么、漏掉了什么，不把生成结果的偶然变化混进代码验证。下面保留完整脚本、实际输出和我做过的改错对照。

## 目录

## 我先区分了三种看起来相似的错误

当前问题是“v2 导入 CSV 报 E102，该怎么处理”。正确依据是 `csv-v2`，正文说明需要检查 `customer_id`。我把可能展示的建议逐条摆出来，再决定每条规则负责哪一种问题。

| 待展示的建议与引用 | 本次集合检查 | 版本检查 | 结论支持检查 |
| --- | --- | --- | --- |
| 添加 `customer_id`，引用 `csv-v2` | 通过 | 通过 | 这条建议得到原文支持 |
| 添加 `user_id`，引用 `csv-v1` | 当前结果没有此 ID | 不再继续 | 不进入展示 |
| 添加 `user_id`，引用 `csv-v2` | 通过 | 通过 | 原文不支持这条建议 |

表格最后一列是我对自编短文的人工核对，脚本并没有自动生成这一列。将三个层次分开后，错误就有了更具体的位置：不存在的标识属于来源关联问题，旧资料属于适用条件问题，合法引用后面的错误字段属于结论支持问题。修复它们需要改动的环节也不同。

## 只信任本次调用实际取回的证据

我没有让检查器拿着回答中的 ID 去整个知识库补查。用户查询 v2 的 E102 时，当前结果只应该包含 `csv-v2`；即使 `csv-v1` 确实在库中，它也不属于这次生成过程的依据。如果展示时再从全库找到它、生成一个能打开的链接，就会掩盖回答并未使用本次证据的问题。

因此，检查器先将本次结果变成 `id → document` 映射，再检查引用是否位于这份映射内。第二步核对版本，看似与上游过滤重复，却能发现缓存或证据组装误把旧文档传入的情况。这个顺序也让我能够分别报告“本次没有取到它”和“本次取到了，但适用条件不对”。

## 运行环境与完整代码

将[知识工具](/examples/agent-lab/knowledge_tool.py)与[引用检查器](/examples/agent-lab/citation_checks.py)放在同一目录。我的本次运行环境为 Python 3.12.14，只依赖标准库和配套模块。

```bash
python citation_checks.py  # 运行五种引用输入和一个语义边界例子。
```

```python
from knowledge_tool import search_knowledge  # 取得本次调用实际返回的证据。

def check_citations(citation_ids: list[str], documents: list[dict], version: str) -> list[str]:  # 只校验来源与版本。
    if not citation_ids:  # 回答没有给出任何引用时先报告缺失。
        return ["缺少引用"]  # 这不是对答案语义的判定。
    evidence = {document["id"]: document for document in documents}  # 为本次检索建立白名单。
    errors = []  # 汇总检查结果，交给调用方决定如何反馈。
    for citation_id in citation_ids:  # 对回答中的每一个引用标识执行相同检查。
        if citation_id not in evidence:  # 全库存在的ID也不能代替本次检索证据。
            errors.append(f"不属于本次检索: {citation_id}")  # 记录越出证据集合的引用。
            continue  # 缺少本次证据时不再访问对应字典。
        document = evidence[citation_id]  # 取到实际被检索到的文档。
        if document["version"] != version:  # 防止上游检索混入其他版本资料。
            errors.append(f"版本不符: {citation_id}")  # 版本冲突与引用不存在分别报告。
    return errors  # 空列表表示这两项校验通过，不表示答案必然正确。

def main() -> None:  # 演示四种结构问题和一个语义边界。
    current = search_knowledge("E102", "v2")  # 当前用户明确使用v2。
    legacy = search_knowledge("E102", "v1")  # 仅用于模拟上游误传旧版本证据。
    cases = [  # 每个样例给出本次证据集合与待检查引用。
        ("正常引用", ["csv-v2"], current),  # ID与版本都对应本次请求。
        ("旧版 ID", ["csv-v1"], current),  # 全库有此ID，但本次没有检索到它。
        ("未知 ID", ["made-up"], current),  # 模拟模型生成了不存在的标识。
        ("混入旧证据", ["csv-v1"], legacy),  # ID在集合内，但版本仍然错误。
        ("没有引用", [], current),  # 没有引用需要单独反馈。
    ]  # 结束五种检查输入。
    for label, citation_ids, documents in cases:  # 用相同函数检查每种情况。
        errors = check_citations(citation_ids, documents, "v2")  # 请求版本始终是v2。
        print(label + ":", errors or "通过")  # 通过只指ID与版本两项条件。
    bad_answer = "请在 CSV 表头添加 user_id"  # 故意给出不适用于v2的错误建议。
    errors = check_citations(["csv-v2"], current, "v2")  # 合法引用仍能附在错误建议后面。
    print("错误建议的 ID 检查:", errors or "通过")  # 复现结构校验无法覆盖语义的问题。
    print("仍需核查:", bad_answer, "；v2 原文要求 customer_id")  # 提醒逐条核对结论支持关系。

if __name__ == "__main__":  # 保证导入校验函数时不会执行示例。
    main()  # 开始本地确定性演示。
```

## 代码逐段解析

### 用本次证据建立白名单

字典推导式 `evidence = {document["id"]: document for document in documents}` 把工具返回值转换为可查找的映射。调用方负责传入真实的检索结果，生成模型只提供待核对的引用标识，不能自行扩充白名单。对于有权限分区的资料，这一点尤其重要：一个全库有效的 ID，并不代表当前请求可以使用对应正文。

这个小实现默认 ID 唯一。继续做真实入库时，我需要在写入阶段检查唯一性，因为字典遇到相同键会用后一条覆盖前一条；仅靠展示阶段查字典，看不出之前是否发生过覆盖。文档修订后也要保留可回查的文本版本，保证旧回答引用的仍然是当时使用的正文。

### 将缺失、越界与版本冲突分别报告

`if not citation_ids` 先处理完全没有引用的情况。循环内的成员检查处理本次集合越界；越界后立即 `continue`，避免继续索引不存在的文档。已经存在于映射中的记录，再进入版本比较。最终返回错误列表，调用方可以根据原因决定补充条件、重新生成或展示适用原文。

我保留具体 ID，是为了排错时能对应回证据组装过程。只返回一个真假值，界面和日志就无法区分资料根本没取到，还是资料取到了却不适用。当前函数只检查这几项条件，输入类型、重复引用和每个断言与哪条资料对应，仍由后续规则补齐。

### 从函数签名确认语义边界

`bad_answer` 被设置为“添加 user_id”，传入检查器的引用仍是 `csv-v2`。仔细看函数签名，它没有接收答案正文，因此也就没有信息去比较建议与原文的含义。这是我这次调试最有用的一步：先检查某种能力需要的信息是否进入了函数，再判断代码能否完成它。

如果继续做语义核对，我会把回答拆成字段、版本、处理动作等可核查断言，为每条断言保留对应证据。像当前这种规则明确的短文，可以先人工核对并补业务规则；开放文本需要更独立的评审方式，还要用人工样本检查评审是否稳定。一个合法 ID 只说明关联成立，不能代替结论支持。

## 实际输出与最后两行的反例

```text
正常引用: 通过
旧版 ID: ['不属于本次检索: csv-v1']
未知 ID: ['不属于本次检索: made-up']
混入旧证据: ['版本不符: csv-v1']
没有引用: ['缺少引用']
错误建议的 ID 检查: 通过
仍需核查: 请在 CSV 表头添加 user_id ；v2 原文要求 customer_id
```

“旧版 ID”与“混入旧证据”是我刻意分开的输入。前者把 `csv-v1` 放在引用里，但当前结果只有 v2，所以报本次集合越界；后者将旧资料直接作为本次证据传入，ID 检查通过，版本检查再把它拦住。它们触发的是不同的防线。

最后两行则保留了结构校验无法发现的问题：引用合法，建议错误。看到“通过”时，我只将其解释为来源与版本没有发现问题，不把这个状态直接变成界面上的“答案正确”。这也避免之后添加更多判断时，检查器的能力范围被无意扩大。

## 我故意关掉一次版本判断

为了确认规则真的能发现目标缺陷，我把版本比较那一行临时替换为下面的条件，再运行同一组输入。这里只替换条件行，不是一个可以单独运行的完整程序。

```python
if False:  # 故意关闭版本冲突分支，只用于观察错误行为。
```

对照结果很清楚：“混入旧证据”由 `['版本不符: csv-v1']` 变成“通过”，未知 ID 仍然报错。这说明第一层检查还在，第二层已经失效。恢复判断后，我再保留原来的正常、越界、版本冲突和语义错误输入，方便后续修改重复核对。

## 这次实验改变了我的排错顺序

如果正确的 `csv-v2` 已经进入上下文，而最后建议仍写成 `user_id`，我会先检查生成和结论支持；扩大 Top-K 可能引入更多旧版本，未必对症。若本次根本没有正确资料，才回到解析、索引、过滤和召回阶段检查。把中间证据保留下来，比盯着最终一段自然语言更容易确定改动位置。

无依据反馈也需要分状态处理。我将缺少版本、成功检索但为空、工具执行失败视为三种情况：缺少条件时先补条件，没有适用资料时说明范围，工具失败时反馈暂时未能完成查询。这样用户知道下一步该补充什么，而维护者能从错误类别找到真正需要修复的环节。

接下来我准备补上重复 ID、文档修订和断言级证据映射。每增加一条规则，先准备一个能让错误实现失败的反例，再观察正常路径是否受影响。这次留下的“合法引用配错误建议”也会继续保留，用来提醒我：引用结构和回答质量需要分别验收。
