在知识库原型开始之前，我先做了一次很实际的区分：用户究竟需要查产品资料、查询当前业务状态，还是希望系统保持某种输出方式。几个目标都可以被包装成聊天，但它们依赖的信息来源并不相同。先选一个流行技术名词，再努力把所有需求塞进去，会让更新、权限和验证变得很难解释。

我的排障场景最终选择了先管理外部资料，再按版本取回依据的路线。这个选择来自资料有版本差异、需要独立更新、回答要能回查，而不是因为每个应用都必须有向量库。下面是我整理选型条件时采用的判断方法，以及一份不调用外部服务的路由实验。

## 目录

## 我先把四种目标分开

我用来区分方案的第一个条件是事实更新方式。产品手册、操作指南和错误码说明可以由文档管理，修改后应让下一次查询使用新资料；订单是否完成、退款到了哪一步，则应从有权限的业务系统读取。后者即使昨天写进了知识库，也不能成为今天状态的可靠依据。

第二个条件是材料规模与选择成本。如果任务只围绕一页固定说明，全文已经能装进实际剩余上下文，直接提供完整材料会省掉索引、召回和排序链路。相反，资料很多、版本不同或更新频繁时，我需要先选出当前问题适用的一部分，避免每次都带上整库内容。

第三个条件是我到底在改变知识还是行为。稳定的分类标签、输出格式和领域表达，可以先用提示与示例验证，再考虑是否值得准备训练数据。微调属于行为适配的候选手段，不应该被当成保存实时订单或保证记住最新手册的方式。我在这组实践中没有执行训练，也没有把一种技术的潜力写成自己的效果结论。

| 路线 | 我考虑采用的条件 | 同时要承担的工作 |
| --- | --- | --- |
| 直接提供全文 | 材料小、固定，已确认上下文余量足够 | 输入预算、资料边界与输出核对 |
| RAG | 资料需要更新、筛选、按证据回查 | 解析、索引、检索、上下文组装与评测 |
| 业务接口 | 需要当前记录或确定性业务计算 | 身份、权限、字段契约与异常处理 |
| 行为适配训练 | 提示与示例不足，且有稳定目标和合格样本 | 数据质量、训练对照、成本与回归 |

这些路线可以同时存在。用户查询退款状态后，还可能需要知道失败原因对应的处理流程；状态来自接口，流程来自适用版本的文档。最终自然语言可以统一展示，数据来源与执行权限仍应保持区分。

## 我用条件表代替技术偏好

下面的脚本把选型条件写成不可变数据对象。它只输出一份明确的决策表，不会调用接口、生成模型或启动训练。我用它检查自己的解释是否前后一致：同一种资料条件发生变化，路线也应该有理由地变化。

代码使用 Python 标准库，保存为 `route_policy.py`，也可[下载脚本](/examples/agent-lab/route_policy.py)。

```python
import json  # 输出每种任务对应的本地路由结果。
from dataclasses import dataclass  # 显式保存选型所依赖的条件。

@dataclass(frozen=True)  # 输入条件不可在判断过程中被悄悄改写。
class Task:  # 这是一份演示决策表，不会实际调用模型或训练。
    name: str  # 任务名称用于核对结果。
    needs_documents: bool = True  # 是否需要产品资料。
    fits_context: bool = True  # 调用方已确认材料是否能装入实际剩余上下文。
    changing_knowledge: bool = False  # 资料是否频繁变化。
    multiple_versions: bool = False  # 是否需要维护版本适用条件。
    live_records: bool = False  # 是否需要当前业务记录。
    behavior_adaptation: bool = False  # 是否要改变稳定的输出行为。

def choose_route(task):  # 让每个选择都能对应输入条件。
    routes, reasons = [], []  # 同一任务允许组合多条路径。
    if task.live_records:  # 实时订单或退款状态应从有权限的业务接口读取。
        routes.append("business_api")  # 不把历史文档当成当前交易状态。
        reasons.append("实时记录先查受授权的业务接口")  # 业务权限仍由应用落实。
    if task.needs_documents:  # 产品规则与排障说明走文档路径。
        if task.fits_context and not task.changing_knowledge and not task.multiple_versions:  # 小而固定的资料可直接提供全文。
            routes.append("long_context")  # 不为单页固定材料额外维护检索链。
            reasons.append("固定短资料已确认可装入剩余上下文")  # 这个布尔量不是用中文字符估算token。
        else:  # 更新、版本或容量条件使外部证据管理更有价值。
            routes.append("rag")  # 先选择适用资料，再组装上下文。
            reasons.append("需要更新、版本筛选或按需提供证据")  # 不宣称所有场景都必需向量库。
    if task.behavior_adaptation:  # 稳定格式与领域表达属于另一种目标。
        routes.append("fine_tune_candidate")  # 只是进入对比评估，不自动启动训练。
        reasons.append("先验证提示与示例，再评估行为适配训练")  # 训练不能保证记住实时事实。
    return {"task": task.name, "routes": routes, "reasons": reasons}  # 同时保留原因便于复核。

if __name__ == "__main__":  # 五种输入不调用网络，也不需要密钥。
    tasks = [  # 通过改变条件观察路线，不用技术名称反推需求。
        Task("固定单页手册"),  # 长上下文可能已经足够。
        Task("多版本排障库", fits_context=False, changing_knowledge=True, multiple_versions=True),  # 当前原型选择的知识管理方向。
        Task("当前退款状态", needs_documents=False, live_records=True),  # 文档不能提供实时交易状态。
        Task("固定分类格式", needs_documents=False, behavior_adaptation=True),  # 训练候选只用于行为目标。
        Task("退款状态加流程说明", fits_context=False, changing_knowledge=True, live_records=True),  # 接口与RAG可以协作。
    ]  # 输入全部为自编演示场景。
    for task in tasks:  # 输出每条决策及其条件解释。
        print(json.dumps(choose_route(task), ensure_ascii=False))  # 不将本地规则称为模型评测结果。
```

## 逐段解析：每个判断都要能回到需求

`Task` 保存的是业务约束，技术路线到 `choose_route` 中才产生。这样做可以避免把“希望使用 RAG”伪装成原始需求。代码里的 `fits_context` 是调用方已经确认过的条件，不是将中文字符数当作 token 数的快捷估算。真正接模型时，还需要计算系统提示、当前问题、工具描述、历史和输出预留，才知道全文是否放得下。

第一条分支优先检查 `live_records`。需要当前交易状态，就把受授权业务接口加入路线。这里的“加入”只表示选择信息入口，没有自动得到业务权限，也没有让模型随意请求任意账户。实际调用还要把可信身份与允许的数据范围落实到应用侧。

文档分支再看容量、更新和版本。小而固定的资料直接走全文；存在需要持续维护的条件时走 RAG。这个规则是为说明当前取舍编写的基线，并不是所有应用的最优决策器。例如，同一份短文也可能需要严格引用位置，检索库也可能只包含很少的文件，都需要结合具体实现再比较。

最后的行为分支与事实来源并列，而不是互相替代。一个系统可以同时使用外部证据和行为适配：先取回当前资料，再让模型按稳定格式处理。但我会分别评估事实是否有依据、格式是否符合约定，避免一个总分掩盖两种问题。`fine_tune_candidate` 的命名也保留了这一层含义，它表示进入评估候选，不代表代码已经训练出了一个模型。

## 五组输入的实际结果

在脚本目录执行：

```powershell
python route_policy.py # 只运行本地决策表，不发起任何收费调用。
```

本次实际输出：

```text
{"task": "固定单页手册", "routes": ["long_context"], "reasons": ["固定短资料已确认可装入剩余上下文"]}
{"task": "多版本排障库", "routes": ["rag"], "reasons": ["需要更新、版本筛选或按需提供证据"]}
{"task": "当前退款状态", "routes": ["business_api"], "reasons": ["实时记录先查受授权的业务接口"]}
{"task": "固定分类格式", "routes": ["fine_tune_candidate"], "reasons": ["先验证提示与示例，再评估行为适配训练"]}
{"task": "退款状态加流程说明", "routes": ["business_api", "rag"], "reasons": ["实时记录先查受授权的业务接口", "需要更新、版本筛选或按需提供证据"]}
```

固定单页资料与多版本排障库得到了不同路线，说明选择来自容量、更新和版本条件。当前退款状态只进入接口路径，固定分类格式只进入训练候选评估。最后一项同时保留接口和 RAG，这正是我希望观察到的结果：技术能够组合，来源责任也仍然清楚。

## 选择 RAG 后，我仍要支付的工程成本

RAG 把外部资料带到模型输入前，但也增加了会失败的阶段。文本可能解析不完整，字段可能被切断，索引可能没有更新，正确资料可能被过滤或排序挤掉。即使证据完整进入上下文，生成时也可能改错条件。因此我不会仅凭架构名字判断它比全文更可靠，而是保留同一组输入比较证据覆盖与最终输出。

全文路线同样有边界。资料装得下只证明容量允许，并不证明模型一定正确使用每一项信息。加入重复、相互冲突或过时的版本，会增加需要核对的条件。长期维护时，更新一份材料与重新发送大量上下文的成本，也需要用实际工作量和调用记录观察，不能先假定某条路线永远更便宜。

对我的排障原型而言，最先值得验证的是版本过滤和来源回查，所以当前先建立了词项与原文抽取的离线链路。后续接入语义检索或模型时，我会继续用同一组问题检查新增能力弥补了什么缺口。方案可以升级，但选择理由应该始终能够回到任务、资料与真实运行结果。
