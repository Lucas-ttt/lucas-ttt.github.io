我在给检索工具补验证时，先做了一个容易误判的对照：查询 E102，不限制版本会返回两份资料；限制为 v2 后只剩一份。前一种结果更多，却把旧版的 `user_id` 处理办法带了进来。对排障任务来说，多出的候选正好可能成为错误答案的来源。

这让我暂时放下“换一个更强检索方案”的想法，先把词项基线、版本条件和失败状态拆开观察。下面的代码用三条自编资料运行，不需要模型或网络。后半部分再用手工排名演示候选融合，记录我对精确线索、语义改写和检索排错的处理思路。

## 目录

## 我先固定输入和预期证据

资料库沿用三个演示 ID：`csv-v1` 是 v1 的 E102，要求 `user_id`；`csv-v2` 是 v2 的同一错误码，要求 `customer_id`；`encoding-v2` 是 v2 的 E201，说明 UTF-8 编码。错误码、版本和来源各自保存，内容相关不代表可以跨版本使用。

运行前，我先把预期写下来：E102 加 v2 只能返回 `csv-v2`，E102 加 v1 只能返回 `csv-v1`。未知 v9 应正常返回空列表，版本缺失则应报告参数错误。前者需要反馈没有适用依据，后者需要补齐条件；如果两者都只显示“没有资料”，后续流程会失去判断下一步的线索。

这里的词项基线按关键词子串命中计分，没有运行 Embedding、BM25 或向量索引。我选择从这个小函数开始，是因为每个候选都能人工解释，适合发现约束是否真的传到了执行层。

## 下载与运行

将[知识检索工具](/examples/agent-lab/knowledge_tool.py)和[检索对照脚本](/examples/agent-lab/retrieval_demo.py)放在同一目录。以下运行记录使用 Python 3.12.14。


## 完整对照代码

```python
from knowledge_tool import search_knowledge  # 复用同目录中的只读检索工具。

def evidence_ids(documents: list[dict]) -> list[str]:  # 只展示稳定的证据标识，方便比较。
    return [document["id"] for document in documents]  # 返回资料ID，不把排序分数当答案可信度。

def search_without_version(query: str) -> list[dict]:  # 故意构造错误版本：合并两个版本的结果。
    documents = []  # 保存尚未按用户版本隔离的候选。
    for version in ("v1", "v2"):  # 逐个查询后直接混合，会丢失用户的版本条件。
        documents.extend(search_knowledge(query, version))  # 这里是本例要暴露的错误设计。
    return documents  # 调用方可能得到同错误码的两套处理方法。

def main() -> None:  # 用同一套演示资料观察正常、空结果与错误参数。
    mixed = search_without_version("E102")  # 先复现未限制版本的候选混入。
    print("未限定版本:", evidence_ids(mixed))  # 输出两份版本不同的证据。
    cases = [  # 以下各项只改问题或版本，便于逐项核查。
        ("限定 v2", "E102", "v2"),  # 新版E102应命中新版字段说明。
        ("限定 v1", "E102", "v1"),  # 旧版E102应保留旧版处理方法。
        ("编码错误", "E201", "v2"),  # 换错误码后应命中编码说明。
        ("未知版本", "E102", "v9"),  # 没有该版本资料时，应得到空列表。
    ]  # 结束固定的四组调用。
    for label, query, version in cases:  # 依次执行，保留标签便于对照输出。
        hits = search_knowledge(query, version)  # 正常调用显式传入用户的产品版本。
        print(label + ":", evidence_ids(hits))  # 把实际结果打印出来，不写预设的通过结论。
    try:  # 单独检查版本缺失的行为。
        search_knowledge("E102", "")  # 空版本不能被静默替换成最新版本。
    except ValueError as error:  # 工具契约用ValueError报告参数问题。
        print("空版本:", error)  # 明确区分参数错误和无匹配资料。
    try:  # 再检查返回数量的边界。
        search_knowledge("E102", "v2", top_k=0)  # 零条不在工具允许的1到5范围内。
    except ValueError as error:  # 参数非法时，不应继续执行检索。
        print("错误 top_k:", error)  # 输出真实校验信息。

if __name__ == "__main__":  # 作为脚本运行时才开始演示。
    main()  # 普通导入不会自动打印或执行演示。
```

## 先看候选，暂时拿掉自然语言生成

这次实际输出为：

```text
未限定版本: ['csv-v1', 'csv-v2']
限定 v2: ['csv-v2']
限定 v1: ['csv-v1']
编码错误: ['encoding-v2']
未知版本: []
空版本: version 必须是非空字符串
错误 top_k: top_k 必须是 1 到 5 的整数
```

我首先比较前两行。未限定版本时，工具返回新旧两份说明；限定 v2 后，旧版被排除。换成 E201，则命中编码资料。未知版本为空，空版本与非法数量明确报错，这些行为与运行前写下的预期分别对应。

脚本只打印 ID，没有生成最终回答。这样做减少了一个干扰：如果结果已经混入 `csv-v1`，问题首先在取数阶段；如果结果恰好只有 `csv-v2`，再去查上下文组装和字段使用。最后一句话是否流畅，不能代替对候选内容的检查。

## 代码逐段解析

### 用一个错误函数复现条件丢失

`search_without_version()` 先查询 v1，再查询 v2，然后直接合并。两个局部查询都能执行，合并结果却不满足当前 v2 请求。这个失败没有涉及模型，也不是少写了一句“优先使用新版”能解决的：错误接口根本没有接收用户的版本条件。

正常调用把 `version` 一直传到 `search_knowledge()`，由它在评分前过滤。以后 Agent 多次调用工具再合并证据时，我也会检查每次参数是否一致，不能把不同时间、产品或版本下的结果直接放在一起。

### 把参数错误和正常空结果分开

两个 `try/except` 观察空版本和非法 `top_k`，只捕获约定的 `ValueError`。如果后续连接外部检索服务，超时、认证失败和集合不存在需要独立状态，不能吞掉异常再返回空列表。否则界面虽然统一了，维护者却不知道应该补资料、修权限还是恢复服务。

当前输出直接打印，便于小实验复查。真正接入应用时，我会把状态、证据列表和错误类别分开记录，同时保留请求标识、过滤条件和候选 ID。日志内容也要控制范围，用户隐私文本和密钥没有必要随着每次排错被完整保存。

### 保持对照只改变一个因素

`cases` 每次只改变版本或错误码，资料和词项规则保持固定。这样才能把变化对应到输入条件。若同时更新语料、切分和检索规则，最终看到一条更好的结果，也很难判断究竟是哪一个改动起作用。

这三条演示资料只用来验证工具行为。我没有把它们的命中结果换算成真实问答准确率；相关性评估需要另外准备问题与参考证据，并保留失败样例。

## 从精确词项走向语义候选

错误码、字段名和编号提供了明确线索，词项路径很适合保留这些标识。但用户也可能说“上传后提示找不到客户字段”，正文中没有这段连续文字，简单子串规则就容易漏掉。我的后续方向是增加语义候选，再用实际模型与真实文本检查它能补回哪些改写。

语义相似也可能找回主题相同、条件不同的资料。无论采用哪种检索信号，版本与可信的访问范围都需要在执行层落实。多路合并后还要按证据身份去重，否则同一条资料被找到两次，就占据两个展示位置，候选数量增加却没有扩大信息覆盖。

我没有直接把词项分数和向量距离相加，因为它们通常不在同一尺度。先按名次建立一个可解释的融合实验，能把“候选怎么合并”和“检索是否有效”分成两次验证。

## 用两份手工排名观察融合

下面两份名单是人工输入，假设已经满足 v2 条件，并非真实 Embedding 搜索结果。我只用它们观察同一资料在不同排序中出现时，名次贡献怎样累加。可[下载独立融合脚本](/examples/agent-lab/rank_fusion_demo.py)运行。

```python
def fuse_rankings(rankings: list[list[str]], smoothing: int = 60) -> list[tuple[str, float]]:  # 对预设名次进行融合。
    if type(smoothing) is not int or smoothing < 1:  # 这里只接受显式的正整数平滑常量。
        raise ValueError("smoothing 必须是正整数")  # 避免非法分母和含糊的布尔参数。
    scores: dict[str, float] = {}  # 证据ID作为键，防止同一资料重复占位。
    for ranking in rankings:  # 逐路处理候选名单。
        if len(ranking) != len(set(ranking)):  # 本例要求单路名单内不重复。
            raise ValueError("单路候选ID不可重复")  # 不让重复项人为增加得分。
        for rank, evidence_id in enumerate(ranking, start=1):  # 明确采用从一开始的名次。
            scores[evidence_id] = scores.get(evidence_id, 0.0) + 1 / (smoothing + rank)  # 累加名次贡献。
    return sorted(scores.items(), key=lambda item: (-item[1], item[0]))  # 降序排列，同分时保持可复查顺序。

rankings = [["csv-v2"], ["encoding-v2", "csv-v2"]]  # 两路排序是手工输入，不是实际模型输出。
result = fuse_rankings(rankings)  # 使用本例显式设定的平滑常量。
print([(evidence_id, round(score, 6)) for evidence_id, score in result])  # 仅为展示四舍五入，不改变排序。
```

实际输出为：

```text
[('csv-v2', 0.032522), ('encoding-v2', 0.016393)]
```

`csv-v2` 在第一路排第一、第二路排第二，得到 `1/61 + 1/62`；编码资料只在第二路排第一，得到 `1/61`。平滑常量六十由这次实验显式设定，名次从一开始，不能把它当成某个数据库的默认配置。

融合分数更高，只说明它在这两份输入排名中的位置更有利。若两条路径都把错误资料放在前面，融合也可能强化错误。因此后续仍要回到标注过的问题上检查覆盖与噪声，公式本身不能提供质量保证。

## 再丢掉一次版本，检查失败是否稳定

我保留了下面这个改错片段。在对照脚本中替换正常的 v2 调用，会重新得到新旧两条证据：

```python
hits = search_without_version("E102")  # 故意丢掉用户给出的v2条件。
print(evidence_ids(hits))  # 实际会得到csv-v1与csv-v2两条证据。
```

这次变化提醒我，不能只用“召回更多”评价优化。候选变多可能扩大覆盖，也可能增加重复、旧版和上下文开销。应该同时检查目标证据、条件约束和最终输入预算，尤其不能让错误版本被更强的排序分数掩盖。

## 我现在采用的逐层排错顺序

遇到原文有答案却没有命中的情况，我先定位解析后的规范文本，确认字段或表格没有在提取时丢失；再查看实际切片，检查错误码、版本和处理动作是否还能够组成可用证据。前一篇已经展示过字段在切片阶段断开的情况，这一步失败时，调大 Top-K 往往只会增加无关候选。

随后检查索引中是否存在当前版本文本，查询表示是否与索引兼容，过滤前后的候选是否满足当前条件。目标资料进入候选后，还要继续看阈值、重排、去重和预算裁剪；若正确证据已经进入上下文，最终却写错字段，再去定位生成与引用一致性。重排能调整已有候选的次序，补不回完全没有进入候选的资料。

目前可运行的部分是词项基线、版本约束、错误分支和手工排名融合。下一步我准备固定一组包含精确编号、自然语言改写和无依据问题的样例，分别记录单路与融合结果，再决定是否值得增加真实向量路径。保留每一步的输入、候选 ID 和失败原因，比先叠加多个检索组件更有利于持续改进。
