用户说“v2 导入报 E102”，Agent 应该查询哪份资料？先别急着接模型、换向量库。下面直接调用工具，用一组固定输入确认返回值是否符合契约。配套脚本已在 Python 3.12.14 运行，数据是三条自编说明，整个演示不需要 API Key。

## 目录

## 面试题

**为什么同时考虑关键词检索和向量检索？用户说“原文有答案却没有答出来”时，怎样定位问题？**

把检索选型与失败诊断放到同一个案例中，可以看清每条路径的职责。主问题是两种检索信号如何互补；失败诊断用于检验是否真正理解每条路径的职责。下面先验证可运行的关键词基线，再用一个独立的小例子解释候选融合，不把排序演示写成已经完成的向量系统。

## 一分钟回答

错误码、字段名和精确编号适合保留词项匹配路径，用户换一种自然语言表述时，可以引入语义向量路径补充候选；两者都必须遵守相同的版本与权限条件。混合检索并不是把两种分数直接相加，而是先验证各自的基线，再去重、融合，必要时重排。遇到“原文有答案”，我会沿解析、切片、索引、筛选、候选、上下文和生成逐层查看中间结果。本例里 E102 的两条资料都相关，但 v1 不适用于 v2；问题先出在条件约束，而不是缺少更强的 Embedding。当前脚本实现的是标准库关键词检索，能够验证版本、空结果与参数错误，不能用于证明向量检索的效果。

## 把预期结果写在调用前面

演示库包含三份资料：`csv-v1` 对应 v1 的 E102，要求 `user_id`；`csv-v2` 对应 v2 的同一错误码，要求 `customer_id`；`encoding-v2` 对应 v2 的 E201，要求 UTF-8。它们的来源、版本和错误码是三个不同字段，不能用“内容看起来相关”代替条件判断。

我们先规定：E102＋v2 只应返回 `csv-v2`；E102＋v1 只应返回 `csv-v1`。未知 v9 返回空列表，表示没有适用资料；空版本则抛出参数错误，表示调用条件不完整。这两种结果需要 Agent 采取不同后续动作：前者说明证据不足，后者先补齐条件。

## 完整对照代码

```python
from knowledge_tool import search_knowledge  # 复用同目录中的只读检索工具。

def evidence_ids(documents: list[dict]) -> list[str]:  # 只展示稳定的证据标识，方便比较。
    return [document["id"] for document in documents]  # 返回资料ID，不把排序分数当答案可信度。

def search_without_version(query: str) -> list[dict]:  # 故意构造错误版本：合并两个版本的结果。
    documents = []  # 保存尚未按用户版本隔离的候选。
    for version in ("v1", "v2"):  # 逐个查询后直接混合，会丢失用户的版本条件。
        documents.extend(search_knowledge(query, version))  # 这里是本例要暴露的错误设计。
    return documents  # 调用方可能得到同错误码的两套处理方法。

def main() -> None:  # 用同一套演示资料观察正常、空结果与错误参数。
    mixed = search_without_version("E102")  # 先复现未限制版本的候选混入。
    print("未限定版本:", evidence_ids(mixed))  # 输出两份版本不同的证据。
    cases = [  # 以下各项只改问题或版本，便于逐项核查。
        ("限定 v2", "E102", "v2"),  # 新版E102应命中新版字段说明。
        ("限定 v1", "E102", "v1"),  # 旧版E102应保留旧版处理方法。
        ("编码错误", "E201", "v2"),  # 换错误码后应命中编码说明。
        ("未知版本", "E102", "v9"),  # 没有该版本资料时，应得到空列表。
    ]  # 结束固定的四组调用。
    for label, query, version in cases:  # 依次执行，保留标签便于对照输出。
        hits = search_knowledge(query, version)  # 正常调用显式传入用户的产品版本。
        print(label + ":", evidence_ids(hits))  # 把实际结果打印出来，不写预设的通过结论。
    try:  # 单独检查版本缺失的行为。
        search_knowledge("E102", "")  # 空版本不能被静默替换成最新版本。
    except ValueError as error:  # 工具契约用ValueError报告参数问题。
        print("空版本:", error)  # 明确区分参数错误和无匹配资料。
    try:  # 再检查返回数量的边界。
        search_knowledge("E102", "v2", top_k=0)  # 零条不在工具允许的1到5范围内。
    except ValueError as error:  # 参数非法时，不应继续执行检索。
        print("错误 top_k:", error)  # 输出真实校验信息。

if __name__ == "__main__":  # 作为脚本运行时才开始演示。
    main()  # 普通导入不会自动打印或执行演示。
```

`search_without_version()` 故意查询两个版本并合并结果，用来复现条件丢失。正常工具没有这种跨版本合并：调用方必须显式传版本。脚本只打印资料 ID，便于看清“候选出现了什么”，不让自然语言答案掩盖取数差异。

## 实际输出

```text

限定 v2: ['csv-v2']
限定 v1: ['csv-v1']

未知版本: []
空版本: version 必须是非空字符串
错误 top_k: top_k 必须是 1 到 5 的整数
```

前两行是关键对照：相同错误码不限定版本时得到两条，限定 v2 后只剩一条。E201 则命中编码说明。这里没有使用“召回更多就是更好”的判断，因为多出来的 v1 资料恰好是不适用于当前请求的候选。

## 代码逐段解析

### 用证据 ID 比较，把生成干扰暂时拿掉

`evidence_ids()` 只取资料的 `id`。这不是最终回答格式，而是为了排查取数阶段：如果这里已经多出 `csv-v1`，就不必先讨论模型的措辞。如果这里恰好返回 `csv-v2`，再往后查上下文拼接与回答是否把字段写错。把候选和自然语言答案分别记录，能够避免“最后看起来答得通顺”掩盖中间阶段的错误。

为了让对照有意义，演示库与查询必须固定。不能一边更换资料，一边改检索规则，最后只挑一条更好的输出来解释原因。`cases` 中分别改变版本或错误码，让每个结果都有明确预期；这也是后续回归测试可以直接利用的输入。当前三个演示 ID 只在这套小资料中使用，不能拿三条样本的通过情况换算真实问答准确率。

### 错误函数故意丢掉哪一个条件

`search_without_version()` 依次查询 v1、v2，再把列表直接合并。它的问题不是少写了一句“请优先使用最新版本”，而是执行接口根本没有接收用户的版本约束。两个查询各自在自己的版本内合法，拼在一起后却不再满足当前 v2 请求。这个例子说明，局部函数成功并不代表组合后的业务语义正确；Agent 多次调用工具后合并证据，也要检查是否把前后不同条件混在一起。

正确调用把 `version` 一直传到 `search_knowledge()`，由该函数在评分前过滤。已知版本没有匹配时返回空列表；版本缺失则进入 `ValueError` 分支。Agent 对前者可以说明暂未找到适用依据，或询问用户是否有对应版本资料；对后者应先补齐条件。返回空列表不意味着系统证明“这个问题不存在答案”，只说明当前工具、当前资料与当前参数没有找到答案。

### 错误分支也属于输出契约

两个 `try/except` 分别观察空版本与非法 `top_k`。这里捕获的是契约规定的参数异常，没有把所有异常都吞掉后伪装成空结果。如果未来连接向量服务，超时、认证失败、集合不存在等错误应有独立记录，不能与“没有命中”混为一谈。否则用户看到同样一句“没有资料”，维护者却无法判断应补文档、修权限还是恢复服务。

实际接入 Agent 时，可以把结构化状态、证据列表和错误类别分开传递；日志还应记录请求标识、过滤条件与候选 ID。日志不应无差别保存用户原始隐私文本和密钥。本文脚本为便于观察而直接打印，尚未实现完整日志与服务错误映射，这些是进一步接入外部系统时要补的环节。

## 关键词和向量分别补哪种缺口

对“E102”“customer_id”这类精确线索，词项匹配便于保留业务标识。对“上传后提示找不到客户字段”这类改写，正文可能没有相同连续词串，纯子串方法容易漏掉。语义向量提供另一种相似性信号，但是否能把这句改写找回来，需要用选定模型和实际文档测试，不能先写结论。官方 [Sentence Transformers 仓库](https://github.com/huggingface/sentence-transformers)分别展示 Embedding 与重排模型的用途，二者也不能当成同一种评分器使用。

两条路的短板同样需要讲清。词项方法可能被别名、拼写或分词影响；向量方法可能找到主题相近却条件不同的资料，例如同样讲 CSV 导入但属于旧版本。无论走哪一路，版本和可信的访问条件都应落实在执行层。候选合并后还要按证据身份去重，否则同一资料被两条路同时找到就占据两个展示位置，Top-K 的覆盖会被高估。

词项分数和向量距离通常不在同一尺度，直接相加会让量纲更大的那一路占优势。可以先用按名次融合的方式建立可检查的基线，再用开发集比较其他方案。[Qdrant 官方混合查询文档](https://qdrant.tech/documentation/search/hybrid-queries/)介绍了 RRF 等候选融合方式。下面只演示其中的名次累加思路，常量由本例显式选择，不代表任一数据库版本的默认配置。

## 一个可以单独运行的候选融合例子

两份名单是人为设置的输入，假设它们已经只包含 v2 的合法候选；它们不是实际 Embedding 搜索结果。本例只回答“同一证据在两路排序中出现时怎样累加”，不回答哪路检索更准确。可[下载独立融合脚本](/examples/agent-lab/rank_fusion_demo.py)直接运行。

```python
def fuse_rankings(rankings: list[list[str]], smoothing: int = 60) -> list[tuple[str, float]]:  # 对预设名次进行融合。
    if type(smoothing) is not int or smoothing < 1:  # 这里只接受显式的正整数平滑常量。
        raise ValueError("smoothing 必须是正整数")  # 避免非法分母和含糊的布尔参数。
    scores: dict[str, float] = {}  # 证据ID作为键，防止同一资料重复占位。
    for ranking in rankings:  # 逐路处理候选名单。
        if len(ranking) != len(set(ranking)):  # 本例要求单路名单内不重复。
            raise ValueError("单路候选ID不可重复")  # 不让重复项人为增加得分。
        for rank, evidence_id in enumerate(ranking, start=1):  # 明确采用从一开始的名次。
            scores[evidence_id] = scores.get(evidence_id, 0.0) + 1 / (smoothing + rank)  # 累加名次贡献。
    return sorted(scores.items(), key=lambda item: (-item[1], item[0]))  # 降序排列，同分时保持可复查顺序。

rankings = [["csv-v2"], ["encoding-v2", "csv-v2"]]  # 两路排序是手工输入，不是实际模型输出。
result = fuse_rankings(rankings)  # 使用本例显式设定的平滑常量。
print([(evidence_id, round(score, 6)) for evidence_id, score in result])  # 仅为展示四舍五入，不改变排序。
```

该例在 Python 3.12.14 的输出为：

```text
[('csv-v2', 0.032522), ('encoding-v2', 0.016393)]
```

`csv-v2` 在第一路排第一、第二路排第二，所以贡献为 `1/61 + 1/62`；编码资料只在第二路排第一，贡献为 `1/61`。更高的融合分数说明它在这两份输入排名中的位置更有利，不说明它有百分之多少的正确概率。假如两条路都把错误资料排在前面，融合也会强化错误。因此还要回到标注过的证据与问题上评估，而不是把融合公式本身当成质量证明。

## 改坏一处，看看哪里变了

把正常的 v2 调用替换为下面两行，仍在本脚本中运行：

```python
hits = search_without_version("E102")  # 故意丢掉用户给出的v2条件。
print(evidence_ids(hits))  # 实际会得到csv-v1与csv-v2两条证据。
```

这个错误容易被误判为“检索覆盖更广”。真正要检查的是调用参数是否传到了执行层，以及返回结果是否仍满足它。之后即使换成向量库，也应先保留版本过滤，再讨论语义召回；过滤条件本身错误，重排模型无法补回业务约束。

这一小例只验证词项和版本的行为。真实资料里的同义说法、跨片段问题、混合检索与重排，需要另建问题集比较；不能用这三条演示数据宣称知识库问答效果已经达标。

## “原文有答案”的逐层诊断

我会先从原文件定位到规范文本，确认解析没有漏掉字段或表格；再看切片，确认错误码、版本和处理动作仍能组合成有效证据。本系列上一篇就演示了完整字段被拆开的失败：这一步没有通过，后面调 Top-K 可能只是增加无关候选。之后核对索引里是否真的写入了当前文本版本、查询是否使用兼容的向量表示，再查看过滤前后的候选是否满足当前条件。

如果目标证据已经进入候选，却没进入最终上下文，继续检查阈值、重排、去重与预算裁剪；如果上下文中证据正确，但回答仍写错字段，才重点检查提示、生成和引用一致性。重排只能重新安排已经拿到的候选，无法让从未进入候选的资料凭空出现。每一步都保存足以复查的文档 ID 与阶段结果，才知道下一次改动应该针对哪里。

## 面试追问

**“是不是所有查询都需要混合检索？”** 不一定。要先比较纯词项和纯向量在同一组问题上的失败类型。若问题主要是格式固定的错误码，先把精确条件和资料质量做好可能更划算；若大量问题是自然语言改写，再验证语义路径的收益。新增路径也会增加维护、查询开销和错误分支，应报告实际结果，而不是只列架构名词。

**“召回越多是否越可靠？”** 候选覆盖有机会增加，但噪声、重复和上下文开销也会增加。当前 E102 例子中，多出的旧版就是有害候选。应同时检查相关证据是否覆盖、错误版本是否被排除、最终上下文用了多少预算，而不是单独追求列表更长。

**“你现在已经实现了哪部分？”** 当前可直接运行的部分是词项基线、版本约束、错误分支和预设排名融合。真实 Embedding、向量索引、多路查询与重排效果尚未由本文代码验证。我能用这些可核对的输出解释职责与排错方法，不把尚未完成的系统能力写成已上线成果。
