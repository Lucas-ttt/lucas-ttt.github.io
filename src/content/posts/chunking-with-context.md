我原本以为，一段文本能够完整拼回原文，每块又都没有超过长度预算，切分就算基本过关了。实际跑一个 CSV 排障小样例后，我发现这两个检查都通过，检索需要的 `customer_id` 却被切成了两半。

这个失败很小，也很有用：正文只有五十四个字符，不需要模型或向量库，就能看清内容是在什么位置失去可检索性的。我保留了这份输入，分别比较十八、二十四和三十六字符的切片预算，记录边界变化，而不是先找一个更大的数字覆盖问题。

## 目录

## 先把长度单位和检查目标说清楚

这次实验里的长度指 Python 字符串的字符数。`len()` 不是字节数，也不等于某个模型的 token 数。我把参数命名为 `max_chars`，避免把十八误读成模型的输入限制。标题、版本和来源单独作为元数据保存，没有占用正文的十八字符额度；以后组装模型输入时，仍要把这些内容算进完整预算。

我为切片设置了三个独立检查：正文能否按顺序拼回去，每块是否在字符预算内，以及是否至少有一块保留完整的 `customer_id`。前两项关注字符和长度，第三项才接近这次排障检索的需求。把它们分开，能直接看出哪一层失效。

位置采用左闭右开区间，例如 `18:36` 对应 `text[18:36]`。我没有在切片函数里额外清理空白或改写文本，目的是让输出偏移始终对应同一份输入字符串，方便逐段回查。

## 完整实现

代码只使用 Python 3.10 及以上的基础语法。保存为 `chunk_context.py`，也可[下载脚本](/examples/agent-lab/chunk_context.py)。演示正文由我为这次实验编写，包含 v2、E102、`customer_id` 和 UTF-8 四种重要信息。

```python
def chunk_document(text: str, title: str, version: str, source: str, max_chars: int = 18) -> list[dict]:  # 按字符预算切分，并保留业务条件。
    if not isinstance(text, str) or not text:  # 拒绝空内容，避免生成没有证据的片段。
        raise ValueError("text 必须是非空字符串")  # 让调用方修正输入。
    metadata = {"title": title, "version": version, "source": source}  # 元数据不混入正文的字符预算。
    if any(not isinstance(value, str) or not value.strip() for value in metadata.values()):  # 检查标题、版本与来源。
        raise ValueError("title、version、source 必须是非空字符串")  # 不默默遗漏适用条件。
    if type(max_chars) is not int or max_chars < 1:  # 布尔值不作为有效字符预算。
        raise ValueError("max_chars 必须是正整数")  # 非正预算无法推进切分位置。
    chunks = []  # 按原文顺序收集片段。
    for start in range(0, len(text), max_chars):  # 每次移动固定数量的字符。
        end = min(start + max_chars, len(text))  # 最后一个片段可以短于预算。
        chunks.append({  # 一个片段既保存内容，也保存回查位置。
            "id": f"{source}#{len(chunks) + 1:03d}",  # 演示标识只在当前切分配置下有意义。
            **metadata,  # 每一段都携带相同的标题、版本与来源。
            "char_start": start, "char_end": end,  # 使用左闭右开的字符区间。
            "text": text[start:end],  # 不清理空白，保证可以准确拼回原文。
        })  # 完成当前片段。
    restored = "".join(chunk["text"] for chunk in chunks)  # 按生成顺序还原正文。
    if restored != text:  # 核查切分过程中是否丢失或重复字符。
        raise RuntimeError("切分结果不能还原原文")  # 这是切分错误，不应交给模型猜测修补。
    return chunks  # 返回可被检索或引用环节消费的片段列表。

if __name__ == "__main__":  # 直接运行，查看实际的切分边界。
    text = "CSV 导入说明。先确认产品是 v2；E102 要检查 customer_id。文件使用 UTF-8 编码。"  # 自编演示原文。
    chunks = chunk_document(text, "CSV 导入", "v2", "demo/csv-v2.md")  # 使用默认的十八字符预算。
    for item in chunks:  # 逐段打印版本、位置与文本。
        print(item["version"], f"{item['char_start']}:{item['char_end']}", repr(item["text"]))  # repr 保留可观察的空白。
    print("拼回一致:", "".join(item["text"] for item in chunks) == text)  # 展示实际还原检查结果。
    print("每段不超预算:", all(len(item["text"]) <= 18 for item in chunks))  # 十八指字符数，不是 token 数。
    print("完整字段命中:", any("customer_id" in item["text"] for item in chunks))  # 演示硬切分把字段拆开的实际问题。
```

## 第一次运行，字段在边界处断开

在脚本所在目录执行：

```powershell
python chunk_context.py # 打印每段的位置与正文，再检查还原、长度和字段完整性。
```

我看到的实际输出是：

```text
v2 0:18 'CSV 导入说明。先确认产品是 v2'
v2 18:36 '；E102 要检查 customer'
v2 36:54 '_id。文件使用 UTF-8 编码。'
拼回一致: True
每段不超预算: True
完整字段命中: False
```

第二段停在 `customer`，第三段从 `_id` 开始。拼回原文时当然能恢复完整字段，但单段检索不会自动拼回全文。如果工具逐段判断是否包含 `customer_id`，它找不到任何一个命中块。这让我把排查重点从模型生成移回切片边界：答案已经在原文里，失败也已经发生在模型调用之前。

## 代码逐段解析

### 输入校验保证循环能够推进

`chunk_document()` 先检查正文、元数据和预算。正文为空时直接拒绝，标题、版本和来源也必须是非空字符串。`max_chars` 要求真正的正整数，避免零步长以及布尔值混入配置。这样可以在进入切片循环前发现无效输入。

这些检查验证的是函数约定，没有证明文件确实存在，也没有证明传入的版本标注正确。我把文档解析、录入核对与切片分开：上游负责交付可信的规范文本，这个函数只处理当前字符串和当前元数据。

### 固定步长只认识位置，不认识业务字段

`range()` 决定每块起点，`min()` 防止末尾越界，字符串切片取得实际正文。这套逻辑容易理解，也能严格限制字符长度，但不会识别字段名、句子或表格。`customer_id` 被拆开正是这个策略允许的结果，程序没有随机出错。

我给每块附上相同元数据，并保存字符起止位置。片段 ID 使用来源加序号，方便本次观察；重新切分后，某个序号对应的正文可能已经改变。后续入库时，需要同时考虑文本版本和旧引用失效，不能假定同样的第三块永远指向同一内容。

### 还原检查依赖无重叠的前提

当前函数没有插入 overlap，所以可以把所有片段直接连接，再与原文比较。这能检查漏字、重字和顺序变化。以后如果相邻片段共享一段文字，直接连接就会产生重复；那时应该按位置检查覆盖范围、缺口和重叠区间，原来的验收规则需要一起调整。

另一个需要保留的前提是文本没有在切片时被清洗。如果先移除空白、替换换行，原始文件的位置通常就不能直接使用。我更倾向于先保存规范文本及其版本，再在同一份文本上计算偏移。当前脚本没有实现 PDF 页码或 OCR 区域映射。

## 只改字符预算，比较三个结果

我固定正文和算法，只改变预算，尽量让输出差异对应一个因素。下面的片段调用同一个函数，也可以[下载参数对照脚本](/examples/agent-lab/chunk_parameter_demo.py)，放在原脚本同目录运行。

```python
from chunk_context import chunk_document  # 导入本篇完整代码中的原函数。

text = "CSV 导入说明。先确认产品是 v2；E102 要检查 customer_id。文件使用 UTF-8 编码。"  # 保持同一份原文。
for size in (18, 24, 36):  # 一次只改变字符预算。
    chunks = chunk_document(text, "CSV 导入", "v2", "demo/csv-v2.md", max_chars=size)  # 使用相同元数据。
    whole_field = any("customer_id" in chunk["text"] for chunk in chunks)  # 检查业务字段是否在单块内完整。
    print(size, len(chunks), whole_field)  # 分别输出预算、块数和字段检查结果。
```

在 Python 3.12.14 中得到：

```text
18 3 False
24 3 True
36 2 False
```

二十四字符时，第二块保留了完整字段；三十六字符时，边界又恰好落在 `customer` 与 `_id` 之间。参数变大，局部信息却重新被切坏了。这是我保留这组实验的主要原因：长度变化不只是“容纳更多文字”，也会移动每一个边界。

二十四也不能直接作为最终选择。这个预算虽然通过字段检查，`UTF-8` 仍被分在两块。我目前只能说，它对这个字段的完整性检查更合适，不能说它对整篇资料或真实检索最好。单独一个平均得分也看不见这种差异，实际片段仍要保留。

## 我怎样看 overlap 的收益和成本

重叠给边界附近的信息多一次进入候选的机会，但不会自动知道哪些词、条件和动作必须一起出现。重叠太短时，长字段仍可能跨界；重叠很大时，重复内容会占据索引、候选位置和模型输入。同一句话在多个块里出现，也可能让 Top-K 看起来很多，实际覆盖却没有增加。

因此我不会把“加大 overlap”当成默认修复。下一步准备先按中文句号、换行和章节组织小单元，再在预算内合并；错误码、字段名和表格标题则增加单独检查。如果合并相邻片段，来源和版本必须一致，避免为补齐上下文而混入其他版本。

长度函数和切分方式也需要一起记录。字符级滑窗与按段落合并的算法，即使用相同重叠数值，生成的实际边界也可能不同。比较配置时，我会保存输入文本版本、每块位置、块数和检查结果，让参数能够对应到具体输出。

## 从这次失败改进后续检查

只查一个字段还不够。后续我会增加“字段完整但版本缺失”“处理动作保留而否定词被切走”“表格值与表头分离”等样例，用它们检查业务信息是否仍然连在一起。长度合法只是一个必要条件，不能替代这些内容检查。

再往后才是检索层对照：固定问题和检索方法，在开发样例中调整策略，再用没有参与调整的问题复核。需要同时看相关证据、噪声和输入开销。目前这份脚本保留的是一个可复现的失败基线，还没有完成端到端策略比较。

这次实验改变了我的排错顺序。遇到原文有信息、结果却没有命中的情况，我先打开规范文本和实际切片，确认目标字段、版本与操作条件是否还处在可用范围内。先把这一步查清楚，后面检查索引、过滤和生成才有明确起点。
