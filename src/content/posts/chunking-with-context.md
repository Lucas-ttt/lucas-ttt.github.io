给每个片段补上版本和来源，检索就不会漏资料了吗？先运行一个很小的反例：正文只有 54 个字符，切分预算设为 18，最终每段都没有超限，也能准确拼回原文，但 `customer_id` 还是被切成了两半。

这篇把切分阶段单独拿出来排错，不接模型，也不安装文本切分框架。目的不是推荐 18 作为真实项目参数，而是让字符边界、来源位置和业务字段的关系直接出现在输出里。

## 目录

## 面试题

**RAG 的 `chunk_size` 和 `overlap` 应该怎么选？怎样证明切片没有切坏业务信息？**

切片参数需要结合语料与检索任务选择。面试时可以用下面的真实失败输出展开：长度检查通过，原文也没有丢字，但检索所需要的完整字段名不存在于任何一个片段中。这个反例能把“程序成功运行”与“切片适合当前检索任务”区分开。

## 一分钟回答

我会先确定长度单位，再根据文档结构和问题类型选择切分策略。`chunk_size` 的含义取决于长度函数，字符数不能直接当成模型 token 数；重叠是补上下文的一种手段，也会带来重复候选和输入开销。比如导入排障资料中，错误码、版本、字段名和处理动作应尽量一起保留。我会先用固定问题观察切片内容，再对照不同参数下的证据命中、噪声和预算，而不是照抄一个大数字。本例中 18 字符切坏了 `customer_id`，改为 24 后这个字段完整，改为 36 却又切坏，因此单纯增大预算并不保证局部边界正确。最终还要检查检索与回答；本例只验证切片层面的可复现行为。

## 输入与预期检查

自编文档说明 v2 的 E102 错误，正文中包含 `customer_id` 和 UTF-8。每段携带标题、版本、来源、字符起止位置和正文。标题等元数据单独存放，没有偷偷拼进 18 字符的正文额度；以后组装模型输入时，仍需另算这些内容的实际 token 开销。

位置采用左闭右开区间。例如 `18:36` 对应 Python 的 `text[18:36]`，便于重新打开原文核对。脚本不删除空白、不插入重叠文本，因此可以用直接拼接检查有没有漏字符或重复字符。

## 完整代码

执行环境：Python 3.10 及以上，仅用标准语法。保存为 `chunk_context.py`，或直接[下载脚本](/examples/agent-lab/chunk_context.py)。

```python
def chunk_document(text: str, title: str, version: str, source: str, max_chars: int = 18) -> list[dict]:  # 按字符预算切分，并保留业务条件。
    if not isinstance(text, str) or not text:  # 拒绝空内容，避免生成没有证据的片段。
        raise ValueError("text 必须是非空字符串")  # 让调用方修正输入。
    metadata = {"title": title, "version": version, "source": source}  # 元数据不混入正文的字符预算。
    if any(not isinstance(value, str) or not value.strip() for value in metadata.values()):  # 检查标题、版本与来源。
        raise ValueError("title、version、source 必须是非空字符串")  # 不默默遗漏适用条件。
    if type(max_chars) is not int or max_chars < 1:  # 布尔值不作为有效字符预算。
        raise ValueError("max_chars 必须是正整数")  # 非正预算无法推进切分位置。
    chunks = []  # 按原文顺序收集片段。
    for start in range(0, len(text), max_chars):  # 每次移动固定数量的字符。
        end = min(start + max_chars, len(text))  # 最后一个片段可以短于预算。
        chunks.append({  # 一个片段既保存内容，也保存回查位置。
            "id": f"{source}#{len(chunks) + 1:03d}",  # 演示标识只在当前切分配置下有意义。
            **metadata,  # 每一段都携带相同的标题、版本与来源。
            "char_start": start, "char_end": end,  # 使用左闭右开的字符区间。
            "text": text[start:end],  # 不清理空白，保证可以准确拼回原文。
        })  # 完成当前片段。
    restored = "".join(chunk["text"] for chunk in chunks)  # 按生成顺序还原正文。
    if restored != text:  # 核查切分过程中是否丢失或重复字符。
        raise RuntimeError("切分结果不能还原原文")  # 这是切分错误，不应交给模型猜测修补。
    return chunks  # 返回可被检索或引用环节消费的片段列表。

if __name__ == "__main__":  # 直接运行，查看实际的切分边界。
    text = "CSV 导入说明。先确认产品是 v2；E102 要检查 customer_id。文件使用 UTF-8 编码。"  # 自编演示原文。
    chunks = chunk_document(text, "CSV 导入", "v2", "demo/csv-v2.md")  # 使用默认的十八字符预算。
    for item in chunks:  # 逐段打印版本、位置与文本。
        print(item["version"], f"{item['char_start']}:{item['char_end']}", repr(item["text"]))  # repr 保留可观察的空白。
    print("拼回一致:", "".join(item["text"] for item in chunks) == text)  # 展示实际还原检查结果。
    print("每段不超预算:", all(len(item["text"]) <= 18 for item in chunks))  # 十八指字符数，不是 token 数。
    print("完整字段命中:", any("customer_id" in item["text"] for item in chunks))  # 演示硬切分把字段拆开的实际问题。
```

## 运行与实际输出

在脚本所在目录，用 Windows PowerShell 执行：

```powershell
python chunk_context.py # 打印每段的位置与正文，再检查还原、长度和字段完整性。
```

本次运行输出：

```text
v2 0:18 'CSV 导入说明。先确认产品是 v2'
v2 18:36 '；E102 要检查 customer'
v2 36:54 '_id。文件使用 UTF-8 编码。'
拼回一致: True
每段不超预算: True
完整字段命中: False
```

第二段以 `customer` 结束，第三段以 `_id` 开始。如果后续工具逐段检查是否包含完整字段名，就没有任何单段能够命中。先保留这份失败输入与输出，再讨论调整切分策略，排错会更直接。

## 代码逐段解析

### 输入校验让切分过程能够推进

`chunk_document()` 先检查正文、元数据和预算。正文不能为空，否则生成空证据没有业务意义；标题、版本、来源必须存在，否则片段即使能检索到也缺少回查条件。预算要求是真正的正整数，既排除了零步长，也排除了把布尔值意外当成数字的情况。校验只证明输入符合这个函数的约定，不证明来源文件真实存在，也不证明传入的版本标注正确，调用方仍需负责文档解析与录入质量。

这里没有对正文执行 `strip()` 或空白归一化，目的是保持位置可核对。如果先清洗再切分，原文件中的字符位置通常就不能直接使用。工程上可以保存清洗后的规范文本及其版本，再基于同一份规范文本计算偏移；如果还要定位原 PDF 页面或 OCR 框，则需要额外的位置映射。本例的偏移只属于传入的 Python 字符串，没有实现 PDF 页面定位。

### 固定步长暴露了边界，而不是保护语义

`range(0, len(text), max_chars)` 决定每次从哪里开始，`min()` 防止最后一块越过文本末尾，`text[start:end]` 决定实际内容。这套算法很容易检查，也能严格控制当前字符长度，但不会识别字段、句子或段落。它只知道数字位置，因此拆开 `customer_id` 并不是程序偶发故障，而是策略允许发生的结果。理解这一点后，排错方向应该是边界策略，而不是让模型在生成时“更认真”。

`id` 使用来源加序号，便于这个演示按顺序核对。若参数从 18 改成 24，第三块的含义就变化了，因此同样的来源加第三块序号不能天然成为永久引用。重新入库时，要决定旧索引怎样失效、旧答案绑定哪个文本版本。这与切片质量属于相邻问题，但不能等到引用已经失效后才考虑。

### 还原检查有前提

代码将所有片段直接拼接，检查结果是否等于原文。这能发现本例中的漏字、重字和顺序变化，是针对“无重叠、无正文改写”策略的有效检查。将来加入 overlap 后，直接拼接会重复重叠区域，不能继续要求结果自然等于原文。那时应按原始位置检查覆盖范围、缺口与重复区间，并确认重叠确实来自同一份文本；测试规则也要随策略改变。

最后的完整字段检查关注的是一个业务不变量：至少一块包含完整的 `customer_id`。它比“长度合法”更接近错误码排障的需求，但仍只覆盖单个字段。还应补“字段完整但缺少版本”“保留处理动作却丢了否定词”“表格值与表头分离”等失败样本。不同检查各自回答一个问题，不能把三个布尔值合并成一个没有解释的总分。

## 参数对照：为什么 36 仍然可能比 24 更差

将下面代码保存为同目录的练习脚本，或[下载参数对照脚本](/examples/agent-lab/chunk_parameter_demo.py)，调用下载包里的原函数。这里没有更换正文，也没有换切分算法，只改变预算，以便隔离原因。

```python
from chunk_context import chunk_document  # 导入本篇完整代码中的原函数。

text = "CSV 导入说明。先确认产品是 v2；E102 要检查 customer_id。文件使用 UTF-8 编码。"  # 保持同一份原文。
for size in (18, 24, 36):  # 一次只改变字符预算。
    chunks = chunk_document(text, "CSV 导入", "v2", "demo/csv-v2.md", max_chars=size)  # 使用相同元数据。
    whole_field = any("customer_id" in chunk["text"] for chunk in chunks)  # 检查业务字段是否在单块内完整。
    print(size, len(chunks), whole_field)  # 分别输出预算、块数和字段检查结果。
```

使用同一函数在 Python 3.12.14 运行得到：

```text
18 3 False
24 3 True
36 2 False
```

预算为 24 时，第二块包含完整字段，但 `UTF-8` 仍被分在两块；预算为 36 时，边界恰好再次落在 `customer` 与 `_id` 之间。由此只能得出“24 对这个字段检查更合适”，不能宣布它对整篇资料最好。这个对照也解释了为什么需要保留原文和具体切片，只有一个平均召回数字时很难看见边界为什么出错。

## overlap 能解决什么，又会增加什么成本

相邻块共享一段文本，能够给边界附近的信息第二次进入候选的机会，但不会自动识别哪些信息必须一起出现。如果重叠太短，某个长字段或跨句条件仍可能跨界；如果重叠很大，索引会出现更多重复内容，Top-K 也可能被相似片段占据，模型输入中同一句话反复出现。这里还要区分字符级滑窗与按段落合并的实现：配置相同的重叠数值，不代表不同切分器一定生成完全相同的边界。[LangChain 官方递归切分文档](https://docs.langchain.com/oss/python/integrations/splitters/recursive_text_splitter)将重叠描述为目标，并说明长度由所配置的函数决定。

因此下一步我会先尝试按中文句号、换行和章节边界组织小单元，再在预算内合并；对错误码、字段名和表格标题设置额外检查。若需要拼接相邻片段，也要让来源与版本保持一致，不能为了凑齐上下文把不同版本合并。当前脚本故意没有实现这些策略，保留一个足够小的失败基线，便于后续改动逐项比较。

## 三个检查分别说明什么

“拼回一致”检查字符没有丢失；“每段不超预算”检查当前计量方式下的长度；“完整字段命中”检查这个业务条件是否还在单段内。前两项通过不能推出第三项通过，更不能推出模型回答正确。

同样，Python 的 `len()` 计算字符串字符数量，不是字节数，也不是目标模型的 token 数。本例明确采用字符预算，避免把脚本中的 18 误读成模型输入限制。换成特定模型的输入预算时，需要使用对应计量并把标题、历史与工具描述一起计入。

## 怎样修改，而不是只换一个更大数字

可以先把预算改为 24，保留同一份原文重新运行，观察字段是否完整、片段数量怎样变化。随后再比较按段落或句号切分、保护错误码与字段名等方案。一次只改一个规则，才能知道变化来自哪里；单个演示字段没有被拆开，不代表所有资料都适合这个参数。

还可以把 `max_chars` 改为 0，观察程序是否在进入循环前拒绝输入；更换标题或版本后，检查每一段的元数据是否同步。本例的片段ID依赖当前来源与序号，重新切分后不应假定旧引用还能指向相同正文，实际入库还需要版本化和引用更新策略。

## 面试追问

**“你最后会怎么定参数？”** 我会准备包含字段、跨句条件、表格和库外问题的小型问题集，固定检索方法与输入预算，比较几种候选策略。先在开发问题上排错，再用未参与调参的问题检查变化是否仍成立。记录每组参数对应的片段、命中证据和输入长度，避免只挑一条成功输出作为结论。本篇尚未进行这组端到端比较，因此没有给出所谓最优参数。

**“把每段切得很大是否就稳了？”** 边界错误可能减少，但无关信息也会增多，多个候选一起进入上下文时更容易超预算。还要考虑 Embedding 模型能接收的输入长度；送给生成模型的上下文预算又是另一层限制。把标题、历史消息和工具描述都排除在预算之外，也会造成计算失真。

**“用户说原文有答案，你先查什么？”** 先找到解析后的规范文本，再查字段是否完整出现在片段里。本例的答案原本就在文中，但单段精确匹配失败已经发生在模型调用之前。只要保留这层中间结果，就能先修切片，再检查索引和检索，而不是一开始就更换生成模型。
