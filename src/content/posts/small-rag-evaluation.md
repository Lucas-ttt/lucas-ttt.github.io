检索工具第一次返回正确的 E102 资料时，我还不能判断它是否稳定。把版本改成 v1、传一个不存在的 v9、将返回数量写成字符串，可能暴露完全不同的失败。因此，我把手动查询整理成八条固定用例，让每次修改都有同一组输入可以对照。

这组回归数据是我围绕三条自编资料写的开发样例。它检查参数校验、版本过滤、关键词命中和空结果，不请求模型。最有价值的结果也不是一次打印出的 `8/8`，而是我故意去掉版本过滤后，三条用例立即失败，能够明确指出被破坏的行为。

## 目录

## 先定义行为，再增加样例数量

相同错误码跨版本出现，是这套资料最容易混淆的条件。如果测试中只有 v2 的一条正常请求，删除过滤后可能仍能看到熟悉的资料，缺陷就被掩盖了。我因此同时保留 v1、v2 与未知 v9，分别验证适用版本和正常空结果。

| 样例类别 | 具体输入 | 我约定的行为 | 希望发现的问题 |
| --- | --- | --- | --- |
| 同错误码、不同版本 | v1 / v2 的 E102 | 分别只返回适用文档 | 过滤被删掉或传错 |
| 有效请求但没有资料 | v9 的 E102 | 正常返回空列表 | 擅自用旧资料填补结果 |
| 参数不合法 | 空问题、空版本、错误数量 | 抛出约定异常 | 静默采用默认值掩盖调用错误 |

前三条有效命中用例期待 `csv-v1`、`csv-v2` 和 `encoding-v2`；未知版本期待空列表；其余四条输入期待 `ValueError`。预期在运行前写定，运行后保留实际结果。如果先看到输出再修改标准答案，回归就失去了发现行为变化的作用。

当前用例比较完整的有序 ID 列表，因此也约束了返回顺序。未来引入同分候选或多路召回时，我需要先明确测试关心顺序还是集合，不能为了让用例变绿就把所有列表转换成集合。排序是否重要，应该由工具契约决定。

## 完整回归脚本

```python
from knowledge_tool import search_knowledge  # 本例只测工具契约，不调用LLM。

CASES = [  # 每条样例明确输入和预期证据ID或异常类型。
    {"name": "v1 的 E102", "params": {"query": "E102", "version": "v1"}, "ids": ["csv-v1"]},  # 旧版字段说明。
    {"name": "v2 的 E102", "params": {"query": "E102", "version": "v2"}, "ids": ["csv-v2"]},  # 新版字段说明。
    {"name": "v2 的 E201", "params": {"query": "E201", "version": "v2"}, "ids": ["encoding-v2"]},  # 编码错误说明。
    {"name": "未知版本", "params": {"query": "E102", "version": "v9"}, "ids": []},  # 没有适用资料属于正常空结果。
    {"name": "空问题", "params": {"query": "", "version": "v2"}, "error": "ValueError"},  # 不接受空输入。
    {"name": "空版本", "params": {"query": "E102", "version": ""}, "error": "ValueError"},  # 不能猜测用户版本。
    {"name": "零条候选", "params": {"query": "E102", "version": "v2", "top_k": 0}, "error": "ValueError"},  # 检查数量下界。
    {"name": "文本数量", "params": {"query": "E102", "version": "v2", "top_k": "3"}, "error": "ValueError"},  # 不默默接受错误类型。
]  # 结束八条固定回归用例。

def run_case(case: dict) -> tuple[bool, str]:  # 每个用例返回通过状态与实际结果。
    try:  # 参数错误是本例需要观察的正常检查分支。
        documents = search_knowledge(**case["params"])  # 原样传入用例中的参数。
    except ValueError as error:  # 只捕获工具契约声明的异常。
        expected = case.get("error") == "ValueError"  # 不把所有异常都当作通过。
        return expected, f"ValueError: {error}"  # 保留真实异常信息供排错。
    actual = [document["id"] for document in documents]  # 只比较明确定义的证据标识。
    passed = "error" not in case and actual == case["ids"]  # 若预期异常却正常返回，也判失败。
    return passed, str(actual)  # 回传实际值，而非只打印一个汇总分数。

def main() -> None:  # 固定顺序执行并报告结果。
    passed_count = 0  # 通过数量从零累计。
    for case in CASES:  # 每条用例独立验证，不依赖前面的结果。
        passed, actual = run_case(case)  # 调用工具并对比预期。
        passed_count += int(passed)  # 将布尔结果转换为通过数量。
        status = "PASS" if passed else "FAIL"  # 用简短状态标记方便查找失败行。
        print(f"{status} {case['name']}: {actual}")  # 同时显示问题和实际输出。
    print(f"工具回归通过: {passed_count}/{len(CASES)}")  # 分母是这八个固定用例。
    raise SystemExit(0 if passed_count == len(CASES) else 1)  # 任一失败都会返回非零退出码。

if __name__ == "__main__":  # 仅直接运行时执行回归。
    main()  # 该结果不是LLM回答准确率或生产质量结论。
```

## 代码逐段解析

### 把输入与预期保存在同一条记录里

`CASES` 中的 `params` 原样传入被测函数，`ids` 与 `error` 表示两种互斥预期。这样查看失败行时，我可以直接从用例回到输入条件，不必再猜这次调用是否偷偷使用了某个默认版本。八条用例独立执行，也不依赖前一条是否成功。

参数异常本身是这里需要检查的正常分支。工具收到空版本却悄悄替换成最新版本，虽然没有崩溃，仍然违背了调用约定；因此失败的定义不是“程序抛了异常”，而是“实际行为与事先约定不一致”。

### 对异常进行双向核对

`run_case` 只捕获工具声明的 `ValueError`。应该命中资料的用例如果抛出它，会因为预期不匹配而失败；应该抛异常的用例如果正常返回，也会被后面的条件判失败。这一正一反，避免把所有异常都算作通过，或者只检查正常路径。

导入错误、字段缺失等非预期异常则直接暴露出来，我没有把它们统一吞掉并改成空列表。否则日志中的“无结果”可能同时代表没有资料和程序故障，定位起来会更困难。错误类别保持清楚，才能知道下一步该改输入、补文档还是修代码。

### 汇总分数前保留逐条输出

`passed_count` 的分母取自用例列表长度，每条实际值先打印，再输出总数。最后的退出码让失败能够被自动化流程识别：任一用例不符合预期，进程就返回非零状态。只有汇总比例看不出哪个条件退化，逐条记录才是我复现问题的入口。

## 我把工具回归和检索指标分开记录

工具回归通过率是通过用例数除以全部用例数。检索的 Recall@K 与 Precision@K 则需要先标注相关证据，两者不能直接套用同一个分母。我用一个组合问题做算术说明：同时询问 v2 必填字段和编码要求，参考证据为 `csv-v2`、`encoding-v2`；假设返回前两条是 `csv-v2`、`csv-v1`，交集只有一条，Recall@2 与 Precision@2 在这个例子中都为二分之一。

这里 Recall 的分母是全部应召回相关项；我约定 Precision 的分母是实际返回项数，返回满 K 时才等于 K。对于不足 K 条和参考集合为空的输入，需要在比较前固定处理规则，不能实验中途换口径。这个算术示例用于解释指标，现有回归脚本没有执行相应计算。

另外，相关证据被召回，也可能在生成时被错误转述。我准备把检索覆盖、引用支持、答案适用性、错误类别和耗时分别记录。版本或权限越界属于需要单列的问题，不适合被一个平均相关性分数冲淡。

## 后续扩充时，我会保留一组没有参与调参的问题

现在这八条已经参与过实现和排错，适合作为开发回归。继续增加同义改写、拼写错误、多证据问题时，我会先固定参考资料和判定依据，再留出没有用来挑参数的问题。看到留出集失败后反复调参，就需要重新承认它已经参与开发，不能继续把它当作未见数据。

每次对照还需要记录语料版本、切片方式、检索规则、过滤条件、Top-K、代码版本和运行环境。这次只关闭版本过滤，所以失败可以与该改动直接关联。未来比较向量模型或候选融合时，也应尽量隔离变量，逐条查看收益与退化。

接入真实模型后，我会另存实际回答与评审依据，对随机生成做必要重复，并保留人工复核记录。样本较小时，展示通过数量和具体错误更便于解释。当前这套小回归的作用，是让每次基础改动都有明确的反馈，再逐步扩展到更完整的问答评估。
