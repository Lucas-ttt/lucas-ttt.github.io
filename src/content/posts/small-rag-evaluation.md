手动问一次 E102，返回了正确资料，还不能确认工具契约完整。版本换掉会怎样？问题为空时会不会继续检索？数量参数传成文本会怎样？下面把这些问题写成八条可重复运行的用例，用实际输出检查工具，而不是凭一次演示判断“效果很好”。

## 目录

## 面试题

**RAG 或 Agent 的测试集从哪里来？怎样设计指标，并证明一次优化有效，而不是恰好答对了演示问题？**

先从可以手工核对的工具回归入手，再讨论检索与端到端问答评估。八条用例是为这个小型工具人工编写的回归集，不是从生产日志抽取的真实用户问题，也不冒充未参与开发的独立测试集。

## 一分钟回答

我会先固定问题、适用条件和参考证据，再分别检查工具契约、检索质量和最终回答。参数错误应按约定报错；未知版本应得到空结果；有答案的问题需要标注相关证据。优化时固定语料快照和其余配置，在同一组问题上逐条比较前后差异，并保留没有参与调参的留出问题。本文先做最小回归：八条确定性用例全部通过，关闭版本过滤后会失败三条。这能证明样例抓住了一个具体缺陷，但不能证明大模型准确率达到百分之百，更不能据此推算真实业务收益。

## 测试集先覆盖行为，再追求数量

在这个资料库里，最容易混淆的是相同错误码对应不同版本。因此用例必须同时包含 v1 和 v2，只有一个版本的“正常问题”测不出过滤缺失。未知 v9 则检查工具是否擅自回退；空问题、空版本、数量范围与类型检查，验证调用约定是否稳定。正常输入与错误输入都属于合同的一部分。

| 样例类别 | 本文的具体输入 | 预期行为 | 想发现的缺陷 |
| --- | --- | --- | --- |
| 同错误码、不同版本 | v1 / v2 的 E102 | 分别只返回适用文档 | 版本过滤被删掉或传错 |
| 有效请求但没有资料 | v9 的 E102 | 成功返回空列表 | 用旧资料冒充当前答案 |
| 参数不合法 | 空问题、空版本、错误数量 | 抛出约定异常 | 静默采用默认值，掩盖调用错误 |

这组数据没有覆盖同义改写、拼写错误、多条证据推理或真实模型输出。后续可以从支持文档、业务人员确认的问题和获得授权后脱敏的失败记录中补充，再由熟悉业务的人核对参考证据。模型生成问题可以帮助发现表达变体，但不能同时让同一个模型无审核地生成标准答案、判分并宣称测试可靠。

## 先决定每个输入应该得到什么

演示库仍是三条自编资料。前三个用例分别期待 `csv-v1`、`csv-v2` 和 `encoding-v2`；未知 v9 应得到空列表；空问题、空版本、零条候选和字符串数量应抛出 `ValueError`。这些预期在调用前就写定，不能看完实际结果再改成“通过”。

证据 ID 完全匹配适合检查这个确定性小工具。如果将来增加多路召回、同分候选或资料更新，要重新明确允许的顺序与证据集合；本例的精确匹配规则不能不加区分地用于所有检索系统。

## 完整回归脚本

```python
from knowledge_tool import search_knowledge  # 本例只测工具契约，不调用LLM。

CASES = [  # 每条样例明确输入和预期证据ID或异常类型。
    {"name": "v1 的 E102", "params": {"query": "E102", "version": "v1"}, "ids": ["csv-v1"]},  # 旧版字段说明。
    {"name": "v2 的 E102", "params": {"query": "E102", "version": "v2"}, "ids": ["csv-v2"]},  # 新版字段说明。
    {"name": "v2 的 E201", "params": {"query": "E201", "version": "v2"}, "ids": ["encoding-v2"]},  # 编码错误说明。
    {"name": "未知版本", "params": {"query": "E102", "version": "v9"}, "ids": []},  # 没有适用资料属于正常空结果。
    {"name": "空问题", "params": {"query": "", "version": "v2"}, "error": "ValueError"},  # 不接受空输入。
    {"name": "空版本", "params": {"query": "E102", "version": ""}, "error": "ValueError"},  # 不能猜测用户版本。
    {"name": "零条候选", "params": {"query": "E102", "version": "v2", "top_k": 0}, "error": "ValueError"},  # 检查数量下界。
    {"name": "文本数量", "params": {"query": "E102", "version": "v2", "top_k": "3"}, "error": "ValueError"},  # 不默默接受错误类型。
]  # 结束八条固定回归用例。

def run_case(case: dict) -> tuple[bool, str]:  # 每个用例返回通过状态与实际结果。
    try:  # 参数错误是本例需要观察的正常检查分支。
        documents = search_knowledge(**case["params"])  # 原样传入用例中的参数。
    except ValueError as error:  # 只捕获工具契约声明的异常。
        expected = case.get("error") == "ValueError"  # 不把所有异常都当作通过。
        return expected, f"ValueError: {error}"  # 保留真实异常信息供排错。
    actual = [document["id"] for document in documents]  # 只比较明确定义的证据标识。
    passed = "error" not in case and actual == case["ids"]  # 若预期异常却正常返回，也判失败。
    return passed, str(actual)  # 回传实际值，而非只打印一个汇总分数。

def main() -> None:  # 固定顺序执行并报告结果。
    passed_count = 0  # 通过数量从零累计。
    for case in CASES:  # 每条用例独立验证，不依赖前面的结果。
        passed, actual = run_case(case)  # 调用工具并对比预期。
        passed_count += int(passed)  # 将布尔结果转换为通过数量。
        status = "PASS" if passed else "FAIL"  # 用简短状态标记方便查找失败行。
        print(f"{status} {case['name']}: {actual}")  # 同时显示问题和实际输出。
    print(f"工具回归通过: {passed_count}/{len(CASES)}")  # 分母是这八个固定用例。
    raise SystemExit(0 if passed_count == len(CASES) else 1)  # 任一失败都会返回非零退出码。

if __name__ == "__main__":  # 仅直接运行时执行回归。
    main()  # 该结果不是LLM回答准确率或生产质量结论。
```

这里有两个细节：一是预期异常的用例如果正常返回，也要判失败；二是只捕获契约声明的 `ValueError`。其他异常会直接暴露，不被统统吞掉并算作“无结果”。最后的非零退出码，方便后续在提交检查中阻止带着回归问题继续发布。

## 代码逐段解析

### 把输入与预期一起固化

`CASES` 中的 `params` 原样进入被测函数，`ids` 与 `error` 表示两种互斥的预期。先写预期再运行，才能防止测试“追着实际输出改答案”。预期包含有序 ID 列表，因此当前脚本也在检查稳定顺序；将来允许多个同分候选时，应先决定测试关心顺序还是集合，而不是简单把所有列表都转成集合来消除失败。

### 异常也要核对是否符合预期

`run_case` 只捕获声明过的 `ValueError`。如果本应返回资料的输入触发它，`case.get("error")` 并不匹配，仍然判失败；如果本应报错的输入正常返回，后面的判断同样判失败。这个双向检查防止“只要没崩溃就算通过”。若出现导入失败、字段缺失等非预期异常，脚本应暴露出来，不能把所有异常都包装成空结果。

### 汇总必须保留原始失败行

`passed_count` 的分母来自用例列表长度，打印每条实际结果后才汇总。最后用非零退出码表达回归失败，便于接入自动检查。只有一个总分看不出是版本过滤、参数校验还是命中规则退化；保留失败输入、实际 ID 和配置，才能复现问题并决定是否接受行为变化。

## 指标怎么算：先写清相关证据和分母

工具回归通过率为通过用例数除以全部用例数，其中包含了异常分支。检索的 Recall@K 与 Precision@K 则需要相关性标注，不能拿这八条混合用例直接代入。以一个同时询问 v2 必填字段与编码要求的组合问题作算术说明：这一次查询的参考证据为 `csv-v2` 和 `encoding-v2`，假设返回前两条是 `csv-v2` 和 `csv-v1`，相关交集只有一条，因此 Recall@2 为一除以二，Precision@2 也为一除以二。这里没有宣称现有脚本已经执行了这套指标计算。

Recall 的分母是全部应召回的相关项；本文约定 Precision 的分母为实际返回项数，返回满 K 时才等于 K。如果系统返回不足 K 条，需要在实验前明确是否仍固定除以 K，不应在不同实验里悄悄换口径。参考集合为空的库外问题也应单独评估拒答或空结果行为，不能直接把除零当作满分。[Ragas 的 ID-based Context Recall](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_recall/)提供了按参考证据 ID 核对覆盖的官方定义。

即使召回全对，最终回答仍可能使用错字段；即使答案听起来正确，也可能没有证据。因此还要单独记录引用支持、答案适用性、失败类型和耗时。权限越界、版本冲突等硬性约束应单列，不宜用平均相关性分数掩盖。

`8/8` 的分母就是代码里的八个用例。它不是大模型回答准确率、用户问题成功率，也不说明系统已经具备生产质量。这里仅检查了这组输入下的参数校验、版本过滤、关键词命中和空结果行为。

```python
if False:  # 故意跳过版本筛选，观察回归能否发现跨版本结果。
```

```text

FAIL 未知版本: ['csv-v1', 'csv-v2']
```

错误版本的退出码是 `1`。恢复条件后重新运行，才回到 `8/8`。这个对照的价值是确认用例能抓住目标缺陷，而不只是确认脚本每次都能打印绿色结果。

## 从工具回归走向问答评估

下一层可以增加完整问题、参考片段、实际回答和人工判定，把证据覆盖、引用支持与答案适用性分别记录。新问题先作为补充样例，不要把已参与修改的八条用例又说成完全未见过的留出集。

这个小集合也没有覆盖中文分词、同义表达、超时、持久化索引或权限。每加入一项能力，先写清预期行为，再补能让错误实现失败的样例。报告结果时保留样本范围、配置与失败明细，方便读者复核每一次改动。

## 面试追问：怎样避免调参把测试集“背下来”

**八条都通过后，能说优化已经完成吗？** 只能说这八条已知行为没有失败。它们参与过实现与排错，属于开发回归；要观察泛化，需要新增没有用于挑选参数的留出问题，且不能看到失败后反复调参又继续把它叫作未见测试。

**前后对照要固定什么？** 至少记录语料版本、切片方式、检索模型或关键词规则、过滤条件、Top-K、代码版本与运行环境。一次只改变待研究因素，并逐条查看收益和退化。本文的对照只关闭版本过滤，因此能把三条失败直接关联到这个改动，没有据此声称“混合检索提升了若干百分点”。

**加入模型后如何报告结果？** 把固定工具回归与端到端问答分开，保存实际回答和评审依据；对有随机性的生成做必要重复，说明评审模型、人工复核和成本。样本只有个位数时，报告通过数量与具体错误比报一个带小数点的高准确率更有解释力。
