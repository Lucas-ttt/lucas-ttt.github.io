我在整理知识检索工具时，先用一个很小的版本冲突检查取数逻辑：同样是 CSV 导入的 E102，v1 要求 `user_id`，v2 要求 `customer_id`。如果只保留错误码和正文，两份资料看起来都相关，后续即使准确复述原文，也可能给出不适用于当前版本的建议。

为了把问题看清楚，我暂时拿掉模型和向量库，用三条自编资料写了一个标准库检索函数。这个实验让我更确定一件事：文档块需要同时保留内容、适用条件和回查入口，不能只是一段孤立字符串。下面记录我的数据结构、实现选择和实际输出。

## 目录

## 我先把资料的身份补完整

我给每条资料保留五个字段：`text` 是正文，`error_code` 是检索线索，`version` 是适用条件，`id` 用来识别本次证据，`source` 用来回查资料。它们各自承担不同职责。相同错误码可以出现在不同版本中，正文相近也不能推出处理步骤通用。

最初看这段小资料时，正文里已经提到版本，似乎没必要再单独存字段。但一旦把版本变成结构化条件，工具就能在执行时直接排除不适用的候选，不必依赖模型从一大段文字里猜测。版本标注仍需要录入时核对；字段存在本身不能保证内容正确。

我把这条约束一直传到函数入口：`search_knowledge(query, version, top_k=3)` 必须显式接收版本，正常返回资料列表。问题和版本都不能为空，返回数量限制在一到五之间。没有匹配资料时返回空列表，参数不完整时则报错。这样上层可以区分“没有依据”和“还缺一个查询条件”。

## 完整实现

代码使用 Python 3.10 及以上版本，不需要密钥或网络连接。保存为 `knowledge_tool.py`，也可直接[下载脚本](/examples/agent-lab/knowledge_tool.py)。

```python
import re  # 使用标准库拆出英文词、错误码与连续中文片段。

DOCUMENTS: list[dict] = [  # 演示资料全部为自编内容，不代表企业真实文档。
    {  # 第一份资料说明旧版本的字段要求。
        "id": "csv-v1", "version": "v1", "error_code": "E102",  # 标识、版本与错误码共同限定适用范围。
        "text": "CSV 导入缺少 user_id 列，检查首行表头。",  # v1 使用 user_id 字段。
        "source": "demo/csv-v1.md",  # 这是演示来源标识，不会尝试打开本机文件。
    },  # 结束第一条演示资料。
    {  # 第二份资料使用相同错误码，但属于新版本。
        "id": "csv-v2", "version": "v2", "error_code": "E102",  # 同错误码不能代替版本过滤。
        "text": "CSV 导入缺少 customer_id 列，检查首行表头。",  # v2 的处理依据改为 customer_id。
        "source": "demo/csv-v2.md",  # 返回来源信息，便于显示依据。
    },  # 结束第二条演示资料。
    {  # 第三份资料覆盖编码问题。
        "id": "encoding-v2", "version": "v2", "error_code": "E201",  # 编码错误使用独立错误码。
        "text": "文件应使用 UTF-8 编码，避免出现乱码。",  # 保留英文编码名称与中文说明。
        "source": "demo/encoding-v2.md",  # 同样使用自编来源标识。
    },  # 结束第三条演示资料。
]  # 结束演示资料列表。

def search_knowledge(query: str, version: str, top_k: int = 3) -> list[dict]:  # 定义只读关键词检索工具。
    if not isinstance(query, str) or not query.strip():  # 拒绝空问题与错误类型。
        raise ValueError("query 必须是非空字符串")  # 明确给出参数错误。
    if not isinstance(version, str) or not version.strip():  # 版本必须显式给出。
        raise ValueError("version 必须是非空字符串")  # 不暗中采用其他版本。
    if type(top_k) is not int or not 1 <= top_k <= 5:  # 真正的整数才可使用，布尔值也拒绝。
        raise ValueError("top_k 必须是 1 到 5 的整数")  # 限制返回规模。
    version = version.strip()  # 清理版本两侧空白，但不猜测版本兼容关系。
    english = re.findall(r"[a-z0-9_]+", query.lower())  # 提取英文词、字段名与错误码。
    chinese = re.findall(r"[\u4e00-\u9fff]+", query)  # 提取连续中文词段，按子串匹配。
    terms = set(english + chinese)  # 去重，避免重复输入人为放大得分。
    ranked = []  # 保存有关键词命中的候选。
    for document in DOCUMENTS:  # 在小型演示资料中逐条查找。
        if document["version"] != version:  # 先按版本过滤，再计算相关分数。
            continue  # 其他版本即使同错误码也不会进入候选。
        content = f"{document['error_code']} {document['text']}".lower()  # 建立可匹配文本。
        score = sum(term in content for term in terms)  # 每个命中词记一分，这不是向量相似度。
        if score > 0:  # 没有关键词命中就不返回资料。
            ranked.append((score, document))  # 同时保留得分与原始资料。
    ranked.sort(key=lambda item: (-item[0], item[1]["id"]))  # 按得分降序，标识用于稳定打破同分。
    return [dict(document) for _, document in ranked[:top_k]]  # 返回副本，避免调用方改动演示库。

if __name__ == "__main__":  # 直接执行时演示三个独立问题。
    for version in ("v2", "v1", "v9"):  # 比较新版本、旧版本与未知版本。
        hits = search_knowledge("E102", version)  # 相同错误码必须受版本约束。
        print(version, [item["id"] for item in hits])  # 输出实际命中的资料标识。
```

## 我用三个版本观察结果

在保存脚本的目录执行：

```powershell
python knowledge_tool.py # 运行三个版本的 E102 查询，不会调用模型或修改文件。
```

这次运行的输出如下：

```text
v2 ['csv-v2']
v1 ['csv-v1']
v9 []
```

v2 只拿到 `csv-v2`，v1 只拿到 `csv-v1`，未知 v9 没有可用资料。我又把问题改成“编码”，版本保持 v2，得到 `encoding-v2`。这组结果把两个独立条件拆开了：错误码决定要找哪类说明，版本决定哪份说明可以用于当前请求。

这里我没有让未知版本自动回退到旧资料。空结果会少给一条看似有用的建议，却能保留请求的原始约束。以后若要支持补丁版本之间的兼容，需要把兼容关系写成明确规则，再补对应测试，而不是在空结果出现时临时猜测。

## 代码逐段解析

### 先校验输入，再处理资料

函数开头的三个条件分别检查问题、版本和返回数量。我单独保留这些判断，是为了让失败原因尽量接近输入位置。空版本应交给调用方补充，v9 则是一个合法但没有匹配资料的查询；两者如果都被包装成“没找到”，后续流程很难决定该澄清还是结束。

数量校验还有一个容易忽略的 Python 细节：`bool` 是 `int` 的子类。只写 `isinstance(top_k, int)` 会接受 `True`，所以这里检查的是 `type(top_k) is int`，再核对上下界。我分别试过空问题、空版本、`True`、零和六，得到的都是明确的 `ValueError`。

`version.strip()` 只去掉两端空白，没有修改版本含义。这样可以接受无意输入的空格，又不会把未知字符串解释成另一个版本。输入规范化与业务兼容是两种不同工作，我倾向于在代码里分开处理。

### 版本过滤放在评分之前

循环先比较 `document["version"]`，不符合条件就跳过。这使旧版资料不会进入本次评分。若先在全库取前三条，再删除旧版，旧资料可能先占满候选，过滤之后反而没有足够的新资料。当前小列表可以直接观察顺序，换成数据库后也需要核对实际查询是否保留同样的业务约束。

版本过滤只处理适用性，没有赋予用户访问权限。如果后续加入私有文档，我会从可信的服务端身份得到访问范围，再限制候选。模型提交一个版本或租户字段，不能成为授予访问权的理由。这部分需要应用接入认证后单独实现。

### 简单评分方便排错，也暴露了局限

正则分别提取英文词和连续中文片段，再用集合去重。重复写两次 E102 不会多得一分；候选按命中数量排序，同分时按资料 ID 保持稳定顺序。这样的规则很直观，我可以打印关键词并逐项检查，适合作为最小检索基线。

它也很容易漏掉自然语言改写。例如“字段不见了”并不一定原样出现在正文中，连续中文片段只有被完整包含才会计分。这里没有分词、同义词扩展或 Embedding，分数也不是正确概率。遇到空结果时，我会先看拆出的词和过滤条件，再决定是否值得引入语义检索。

### 返回资料副本，继续保留证据

最后一行返回字典副本，调用方拿到的仍然是正文、版本、ID 和来源。如果工具只返回“补一列即可”，后续就难以复查依据，更难发现字段名被写错。现在字典的值都是字符串，浅拷贝可以隔离顶层字段修改；若以后加入嵌套列表，还需要重新检查共享对象，不能把这一行视为通用深拷贝。

我也把“可以回查”与“结论正确”分开。返回正确的 `csv-v2` 后，模型仍可能把 `customer_id` 写成 `user_id`。因此元数据只是后续校验的基础：还要检查引用是否属于本次检索，以及具体建议是否被正文支持。

## 这次实践留下的几个取舍

我先追求调用行为稳定，再考虑召回更多资料。对这个排障场景，适用版本正确比列表更长更重要。来源、标题和标识能帮助排查问题，但它们不会自动修复错误标注，也不会代替对正文含义的核对。

资料增量更新后，ID 的稳定性也需要重新设计。如果重新切分后把旧 ID 绑定到新内容，历史引用会悄悄改变含义。我计划让引用能够绑定到明确的文本版本，并保存足以回查的位置；当前三个演示 ID 只用于这次独立实验。

后续扩展产品字段时，我会先补资料和输入约定，再在评分前加产品过滤，保留“同版本、同错误码、不同产品”的前后输出。最后才把这个函数注册为 Agent 工具，让模型提交参数，由程序执行。这样每增加一个条件，都能在接入生成之前观察到实际取数是否改变。
