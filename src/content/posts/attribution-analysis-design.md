做退款金额查询的实验时，我先写出了一个能够执行的分组求和，随后只把状态从 `success` 改成 `pending`：SQL 仍然合法、只读，金额却从 350 元变成了 999.99 元。这次对照让我把两个容易混在一起的目标分开了：约束查询能做什么，以及核对查出的数字是否符合业务问题。

我把数据缩到五条自编记录，放进 SQLite 内存数据库。先手工算出预期，再测试查询、语法错误后的修正和写入拒绝。示例中的 SQL 都由代码预设，没有让模型生成查询；这让我可以先验证执行工具本身，再考虑后续接入 Agent 时的决策问题。

## 目录

## 先把“十月成功退款”的口径写清楚

退款可能按申请时间、支付时间或成功时间统计，金额也可能指申请额、实退额或扣除手续费后的净额。我的实验将 `day` 定义为演示记录的状态时间，将 `status=success` 定义为成功退款，金额列 `cents` 使用整数分。先固定这些条件，才能判断查询结果是否正确。

五条记录中，十月成功退款分别为 120 元、80 元和 150 元，合计 350 元；另外保留一条十月未成功记录 999.99 元，以及一条十一月成功记录 50 元。后两条并非凑数据，而是分别检查状态过滤和月份边界。缺少这些反例，筛选写错后也可能得到一个看起来合理的数字。

日期使用左闭右开范围，即十月一日及之后、十一月一日之前；状态单独绑定为 `success`。我把金额转换留在显示边界，在数据库里始终存整数分，方便逐项核对。这里做的是按渠道分组的金额查询；若继续实现渠道归因，还需要定义关联关系、归因窗口和多次触达的分配方式，不能用分组求和代替这些规则。

## 运行环境与完整代码

本次使用 Python 3.12.14 的标准库，不连接真实业务数据库。解压[完整示例](/examples/agent-lab.zip)后进入 agent-lab 目录，也可以单独[下载 sql_readonly.py](/examples/agent-lab/sql_readonly.py)。

```python
import sqlite3  # 用标准库 SQLite 演示只读查询，不连接真实业务数据库。
from decimal import Decimal  # 用十进制定点转换分与元。
from time import monotonic  # 为每条查询设置执行时间边界。

def create_demo():  # 创建仅存在内存中的自编退款资料。
    db = sqlite3.connect(":memory:")  # 进程结束后演示库自动消失。
    db.execute("CREATE TABLE refunds(day TEXT, cents INTEGER, status TEXT, channel TEXT)")  # 金额始终存整数分。
    rows = [("2026-10-02", 12000, "success", "搜索"), ("2026-10-15", 8000, "success", "搜索"), ("2026-10-23", 15000, "success", "推荐"), ("2026-10-26", 99999, "pending", "推荐"), ("2026-11-01", 5000, "success", "搜索")]  # 五行资料覆盖状态与跨月边界。
    db.executemany("INSERT INTO refunds VALUES (?, ?, ?, ?)", rows)  # 初始化使用参数绑定。
    db.commit()  # 初始化结束后再收紧查询连接。
    db.execute("PRAGMA query_only = ON")  # 在该连接上开启只读模式。
    allowed = {sqlite3.SQLITE_SELECT, sqlite3.SQLITE_READ, sqlite3.SQLITE_FUNCTION}  # 此演示只允许查询所需动作。
    db.set_authorizer(lambda action, *args: sqlite3.SQLITE_OK if action in allowed else sqlite3.SQLITE_DENY)  # 在数据库执行层拒绝写入和其他动作。
    return db  # 返回受到约束的演示连接。

def checked_query(db, sql, parameters=()):  # 新查询和修正后的查询使用同一个入口。
    deadline = monotonic() + 0.2  # 每次入口建立独立的查询预算。
    db.set_progress_handler(lambda: int(monotonic() > deadline), 1000)  # 周期性检查执行预算。
    try:  # 执行前校验与真正查询均在同一权限连接上完成。
        db.execute("EXPLAIN QUERY PLAN " + sql, parameters).fetchall()  # 每次都重新检查当前 SQL。
        return db.execute(sql, parameters).fetchmany(20)  # 控制返回条数，避免把无限结果交给模型。
    finally:  # 无论成功失败均清理本次预算回调。
        db.set_progress_handler(None, 0)  # 不把上一次截止时间带入下一次查询。

if __name__ == "__main__":  # 直接运行即可观察正常、修正与拒绝分支。
    db = create_demo()  # 所有演示数据在本次运行内创建。
    parameters = ("2026-10-01", "2026-11-01", "success")  # 日期采用左闭右开范围。
    sql = "SELECT channel, SUM(cents) FROM refunds WHERE day >= ? AND day < ? AND status = ? GROUP BY channel ORDER BY channel"  # 分组与总额使用相同条件。
    try:  # 主查询只统计已成功的十月退款。
        result = checked_query(db, sql, parameters)  # 实际执行受约束的查询。
        for channel, cents in result:  # 按渠道显示查询结果。
            print(channel, f"{Decimal(cents) / 100:.2f} 元")  # 只在显示边界把分转换成元。
        print("合计", f"{Decimal(sum(row[1] for row in result)) / 100:.2f} 元")  # 核对分组加总。
        try:  # 人为制造一次语法错误。
            checked_query(db, "SELEC SUM(cents) FROM refunds")  # 错误不会被当作金额为零。
        except sqlite3.DatabaseError:  # 记录失败后提交另一条查询。
            total = checked_query(db, "SELECT SUM(cents) FROM refunds WHERE day >= ? AND day < ? AND status = ?", parameters)  # 修正查询重新走校验。
            print("修正后复验", total[0][0], "分")  # 输出与分组结果相互核对。
        try:  # 验证数据库层面的写入约束。
            checked_query(db, "DELETE FROM refunds")  # 此语句应被数据库拒绝。
        except sqlite3.DatabaseError:  # 捕获拒绝，不尝试其他路径执行。
            print("写入请求被拒绝")  # 只输出状态，不隐藏失败原因。
    finally:  # 演示结束时释放内存连接。
        db.close()  # 不在用户磁盘创建业务数据。
```

## 代码逐段解析

### 初始化后，再把连接收紧

`create_demo` 先建表、写入五条记录并提交，然后开启 `query_only` 和授权回调。我将初始化与查询阶段分开，因为前者需要写入，交给查询工具后才应该进入受限状态。回调只放行本例所需的 SELECT、READ 和 FUNCTION，其他动作返回拒绝；写入限制落实在这条数据库连接上。

这个回调没有细分表、列和函数名，因此当前实验只验证这条连接的动作约束。继续连接真实数据时，我还需要加入对象白名单、数据范围和独立业务授权。参数绑定也有明确职责：日期、状态作为值传入，不参与拼接；它不能代替对整条模型生成 SQL、表名或列名的审核。

### 所有查询都进入同一个检查函数

`checked_query` 是我保留的唯一执行入口。新语句与修正语句都先经过 `EXPLAIN QUERY PLAN`，再实际执行，并在 `finally` 中清理进度回调。这样语法错误后即使换了一条 SQL，也没有为了“先把结果跑出来”绕开检查。

执行计划可以帮助暴露语法、对象和权限问题，但本例没有分析计划并拒绝某类扫描。即使 EXPLAIN 成功，月份与状态也可能写错。我的金额变体正好说明了这一点：数据库知道如何执行，不代表它知道这次业务目标是什么。

`SELEC` 是人为注入的语法错误，捕获异常后提交一条固定修正语句，并再次调用同一个入口。这次只验证了一次修正路径。未来接入动态生成时，还应限制修正次数，并保存每个候选与错误，避免在同一失败上循环尝试。

### 预算和返回规模分别约束不同资源

每次进入函数时，`monotonic()` 建立新的截止点；进度回调周期性检查，超过预算返回非零状态。由于检查发生在一定数量的虚拟机指令之后，`0.2` 秒是这个实验的近似执行预算，不能据此推导所有阻塞都能在同一时刻强制终止。

`fetchmany(20)` 则限制取回的行数，不限制数据库实际扫描或聚合的行数。两种限制不能互相替代。我还注意到一个展示边界：当前只有两个渠道，取回结果可以完整求和；若分组超过二十个，直接将局部返回值相加就会漏算。后续要标记截断、分页，或用相同条件另查总额。

## 正常查询与一次修正的实际输出

```powershell
python sql_readonly.py # 运行内存数据库中的查询、纠错与写入拒绝。
```

```text
推荐 150.00 元
搜索 200.00 元
合计 350.00 元
修正后复验 35000 分
写入请求被拒绝
```

搜索渠道的两条记录为 120 元和 80 元，推荐渠道为 150 元；分组加总得到 350 元，独立总额查询得到 35000 分。我再回到五条明细核对，确认 pending 记录与十一月记录都没有进入结果。分组查询和总额查询一致还不够，因为它们可能复制同一个错误条件，明细是这里的第三个核对依据。

最后的“写入请求被拒绝”来自对 DELETE 的实际尝试。它只说明这条受限连接拒绝了当前操作，不代表模型生成 SQL 的质量已经得到验证。工具执行与查询决策仍是两个需要分别观察的环节。

## 只改状态，合法查询也会得到错误目标

我将主程序 `parameters` 的最后一项从 `success` 改成 `pending`，保持日期、SQL 和数据不变。这个变体的实际输出如下：

```text
推荐 999.99 元
合计 999.99 元
修正后复验 99999 分
写入请求被拒绝
```

结果变成 999.99 元，修正后的独立总额也同步变成 99999 分，写入限制仍然生效。单看 SQL 是否可执行、两个结果是否一致，发现不了统计对象已经变化。回到最开始写定的“十月成功退款”，才能看到状态条件与需求不符。

因此，我把业务核对放在执行之后单独保留：统计对象是什么，日期列表示什么，包含哪些状态，金额单位如何换算。后续生成报告时，也需要将数字与这些条件一起传递，而不是只给模型一段没有口径的结果表。

## 空结果、查询失败和零金额分别处理

这次数据包含明确的成功记录，继续扩展时还要覆盖没有匹配记录的情况。`SUM` 在没有输入行时可能返回空值，是否展示零元应依据已确定的业务规则处理。语法错误、超时或权限失败则应该保留为失败状态，不能为了页面显示整齐就统一替换成零。

我准备在查询记录中保留问题、已确认口径、SQL、绑定参数、执行状态和结果范围。这样某个报告中的金额出现疑问，可以回到对应条件复现。涉及真实业务数据后，记录本身也需要脱敏与访问控制，避免排错日志变成另外一个数据出口。

## 从内存实验走向真实服务

迁移到其他数据库时，我会重新验证只读账号、表列授权、查询超时和返回截断，不能直接照搬 SQLite 的连接回调。身份与数据范围也需要由可信的应用层绑定，不能由模型任意填写。对于写入操作，我会使用独立工具与确认流程，让查询能力和资金动作各自拥有清楚的边界。

这次实验留下了三个可以重复观察的结果：正常口径得到 350 元；错误状态得到 999.99 元；写入请求被拒绝。它们分别检查业务条件、对照结果和执行限制。把这三个层次分开之后，后续接入 SQL 生成、纠错和报告环节时，也就有了可以继续复用的检查入口。
